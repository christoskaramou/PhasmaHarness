# Phasma Harness

Desktop client (Windows and Linux) for local coding agents. Create named agents with separate instructions, models, workspaces and conversations. Codex, Claude Code, Cursor CLI and DeepSeek Harness CLI can run Hub and workers; Muse Code and Antigravity CLI are additional worker providers. Smart routing can pick a model, or you can choose one.

Antigravity currently accepts text workers with Full access. Ask, Workspace, images and Hub routing are unavailable for this adapter. Sign in with `agy` in your terminal, then connect it in Settings.

## Shared MCP connectors

Harness includes **Context7**, **Microsoft Learn**, and **OpenAI Docs** as enabled documentation connectors. New installs get them automatically; upgrades add only missing entries and preserve existing names, endpoints, credentials and permissions. Editing, disabling or removing a default is permanent across restarts. Connections open when used, so startup works offline. Context7 supports an optional personal API key for higher limits; no shared key ships with Harness.

Use **Settings → Connectors → Add connector** to connect a remote Streamable HTTP MCP server or a local stdio program. The connection belongs to Harness and is available to Hub, normal bots and sub-bots with any supported CLI or API model. No provider-specific MCP configuration is required. Bots discover tools with `connector_tools` and run them with `connector_call`.

Connector configuration changes do not require a restart. Settings refreshes the saved `connectors.json` while the tab is open (every two seconds); bots also reload it before discovering or calling tools. External edits must keep the version-1 format and unique connector IDs; replace the file atomically when possible. Invalid or incomplete files leave the last loaded configuration intact and show an error until repaired. Keep credentials in Settings so they stay encrypted. Changed or removed connectors close their old sessions, while unchanged connections remain open.

Remote servers support no authentication, a bearer token, or browser OAuth. Local programs accept one argument per line, an optional working directory and encrypted environment variables. They run as your OS user; only add programs you trust. Each bot conversation gets its own server session/process. Credentials are encrypted with the OS key store and never included in bot tool discovery. If OS key protection is unavailable (including the current headless runner), only connections without saved credentials are supported. OAuth sign-in must finish in a browser on the runner computer.

**Confirm each call** is the default, including for Full-access bots. You can explicitly allow a connector for Full-access bots; Ask and Workspace bots still require confirmation. Stop cancels the bot's pending call. A cancelled or failed remote action may already have completed, so Harness does not retry it automatically. Disconnect disables the connector for all bots; Forget credentials removes its saved authorization.

This initial integration exposes MCP **tools**. MCP resources, prompts and legacy HTTP/SSE servers are not included. Use Connect in Settings to reload a changed server catalog. Third-party account sign-in has not been live-tested; protocol, permissions, UI and adapter tests use local servers without paid inference. The three bundled documentation endpoints have also passed live read-only requests.

## Conversation commands

Type `/` to show every command above the composer; keep typing to filter command names without case sensitivity. Use ↑/↓ to select, Enter or a click to run, Tab to complete without running, and Escape to dismiss. `/help` and **Commands /** under **Options** also open the full command list. Commands run locally against the selected agent and are never sent as model prompts or routed through Jev. `/compact` compacts Codex/Claude context while keeping the visible chat; Cursor has no manual compaction. `/clear` asks for confirmation, archives the current chat locally and starts a fresh provider conversation without changing the agent, role, workspace or access. **Clear** and usage details are available under **Options**. Cancel keeps the conversation and draft unchanged; confirming clears the draft and attached images. Active or pending work must finish or be stopped/resolved first. `/stop` stops the selected agent and its pending child tasks, `/agents` opens the overview, and `/settings` opens settings. Commands take no arguments; unknown commands are reported locally. The full slash-command handler is in `ui/app.js`.

Harness confirmations use matching in-app dialogs, including Clear and provider removal/install. Dialogs receive focus without selecting a button; Enter does not activate buttons or submit forms, and Escape cancels. Startup errors share this style. File and folder pickers remain native.

## Local agents

Batch jobs use separate project copies. Fresh project folders work too; creating a Git repository first is optional. Automatically created batch workers leave the sidebar after finishing and stay in **Overview** with their history. Open one there, or Edit and save to keep it as a regular bot. Explicitly created bots stay in the sidebar.

Start with **Hub**, the permanent coordinator. It keeps a fixed chat model, delegates execution to existing or new workers, and brings their results back. Hub Auto asks Jev or Smart Routing to choose a balanced mid-tier model from the enabled catalog, using available benchmark evidence and model descriptions rather than a model-name list. With enough comparable benchmark evidence, measured extremes are excluded before routing; unknown measurements stay eligible. Configurable effort is limited to Low or Medium, with Low preferred when adequate; models without effort controls use their provider default. A sole eligible model is selected directly without a routing call. The choice stays pinned; if no supported effort is available, enable a model or choose Hub's model manually. Worker routing is unchanged. Workers use Auto unless you request a model and effort. Hub stays available while they work and summarizes older chat context automatically; `/compact` is also available, and `/clear` still asks for confirmation. Use the **+** in the sidebar toolbar to create an agent manually, then select it to chat. Saving stores the profile immediately; provider connections start in the background, reusing the main controller's Claude/Cursor discovery. **Overview** shows cards with each agent's role, workspace, model, access and activity, plus Open, Edit, Stop and Delete actions. Right-click a sidebar entry or Overview card for its available actions; Shift+F10 opens the same styled menu from the keyboard, with Delete in red. Deletion is blocked while work or results are pending, and keeps local conversation files for recovery. Starting and connection errors stay visible. **Hub** is pinned above the agent list and cannot be deleted. Every agent opens one persistent conversation; existing additional visible chats become named agents on startup, except group chats. Archived history stays on disk. The old session list and New session controls are removed; Ctrl+N creates an agent. Settings is at the bottom of the sidebar. New agents default to Ask access; choose Workspace access when they should edit files. Provider accounts and model availability remain shared.

Hub has its own pinned area above the other bots. Rename it with **Rename** on its Overview card or its right-click menu; it answers to the new name, and no bot can take that name, "hub" or "main". Specialist rows show a short activity/latest-reply preview; detailed status and actions remain available in Overview and the context menu. Settings → General → Appearance offers **Dark**, **Light**, and **System** (default), saved locally and applied immediately. System follows your device appearance. Advanced model, effort, and worker-routing controls are under **Options** beside the composer.

Create a group from **Overview → New group**, name it and choose existing bots. Hub coordinates; groups appear beneath its pinned area. Use the header’s **@mention** picker or start a message with `@Name` to send it to one member. Other messages go to Hub. The result returns to that group, with no automatic broadcast to other members. Groups keep separate histories, drafts, queues and job activity. Membership keeps each bot’s existing access; Stop affects the selected group, and Clear retains its members while archiving the old chat. Use the header’s **Group** button to edit members or archive an idle group.

Routines are set up only by asking in chat, for example “every weekday at 9 ask me how the build is going”, “on 2026-11-02 at 10:00 remind me to send the release notes” or “whenever I commit, review the new commit”. A routine sends its text back to the agent, in the chat where you asked, on a schedule (weekdays, local time and timezone), once at a date and time (it then removes itself), or on each new local Git commit. Ask “what routines do I have?” to see them, or ask to change, pause, resume or remove one. Hub sees and changes every routine; a bot sees only its own, and a bot’s routines are deleted with it. Only messages you type can change routines; results, bot messages and routine runs cannot. Missed runs coalesce, and a routine waits for its previous run to finish.

Direct chats stay separate from delegated execution contexts. Background assignments share two FIFO execution slots; an idle helper wait releases its slot. Foreground chat remains available. Independent Git batch jobs use registered project copies; ordinary shared-workspace tasks can still conflict when editing the same files. Provider limits and local inference-server locks still apply. Closing the window leaves the runner working; reopen it from the tray. Explicit Quit stops owned work, and unconfirmed cleanup blocks new admission.

Every agent, including **Hub**, can create another agent with `agent_create`: give it a unique name and role instructions. Agent-created agents default to **Auto**. When you request a specific model, the creator uses `agent_models` to find available choices and supported efforts, then passes the model's `mode` and, only if requested, `effort`. For example: “Create a Reviewer using gpt-6.1-sol with high effort.” Unavailable models and unsupported efforts are rejected. Auto chooses effort within the configured cap. The new agent inherits the creator's current conversation workspace and access, appears in the sidebar immediately, and starts its provider connection in the background. Creation alone does not start a task or change the creator's model.

Agents can manage other agents through chat: `agent_stop` and `agent_set_access`. For example: “Stop Test211” or “Set Test211 to Ask access.” No agent, including Hub, can delete an agent; only you can, from the app. Stop pauses replies and pending child tasks; it reports stopping until active work settles. Deletion keeps conversation files for recovery and refuses pending work. Access changes update the profile default and current conversation, require an idle agent, and cannot exceed the caller’s current conversation access. Changing access in another workspace requires Full access. Children inherit the creator’s current access at creation, including agents created by other agents; existing children keep their own configured access.

Agents can read each other's current conversation with `agent_read_context`, including Hub. For example: “Read Researcher's findings about the renderer.” It reuses the large-output reader: search by `query`, then read exact `line`/`column` excerpts, capped at 30 lines and 8,000 text characters per call. Visible messages and recorded tool results are included; private reasoning, hidden instructions, pending messages and user image attachments are excluded. Reads do not start work on the other agent. Same-workspace reads are allowed; another workspace or a Full-access conversation requires Full access. Results are live, partial evidence with a conversation reference and hash, not an automatic copy of the entire context.

Ask an agent to send text and a task to another agent using `agents_list` and `agent_delegate`, for example: “Send this text to Test211 and ask it to review it.” Any agent can request work from any other idle agent, including Hub (`agentId: main`). The task contains the request and pasted text, with whitespace preserved; results return to the sender. The old Delegate controls and dialog are removed. Workers receive agent tools through the bundled MCP for Codex (including existing conversations), Claude and Cursor; Hub uses the same validated agent controls through its restricted chat runtime. The task text is sent to the target agent's existing conversation. A busy target must finish before accepting another delegation. Only the new task's results return to the source. Results queue back into the requesting conversation for an automatic continuation, unless that conversation was stopped. If its queue is full, the result is added to the visible conversation instead. Named agents can send at most three tasks per request; Hub can send up to ten, including automatic continuations. Ask Hub to create several independent workers for the same task and it dispatches the requested count as one batch, retaining any requested model and effort and collecting all results before claiming completion. Batch workers run independently in shared workspaces as well. Agents doing delegated work can ask other agents for help; self-requests and circular task chains are rejected. A parent waits for child results and its continuation before returning its completed result. Waiting agents retain a Stop action; stopping a requester also stops its pending descendants and pauses automatic replies. The pending task queue is bounded at ten.

Delegation never increases the source conversation's access level. Sending tasks across workspaces requires Full access. Approvals stay separate per agent. Interrupted delegated tasks are marked after restart and never automatically replayed. Profiles, conversations and queues are stored locally beside the existing session store. Models still use the configured providers; this feature does not install offline models or add a browser/desktop automation runtime. Work requires the app and computer to remain running.

Architecture and validation: [local agents](docs/wiki/local-agents.md).

## Background allowance

The overnight guard pauses new background turns once a reported allowance is full. It uses ChatGPT reports and available Claude Code plan reports. Claude checks use the native CLI without model calls or transcript scans. Settings shows the last report for the matching account. Unknown allowance stays unknown, and a running call can finish past it. Other providers' remaining quotas are not yet reported here. Real Max-window acceptance is still pending.

## Browser access

An optional Linux runner works without Electron or a display. See [Linux service setup](docs/wiki/hosting.md) for installation, native provider sign-in and private HTTPS access. Public-host and real-device acceptance remain in progress.

In desktop Settings → General → Browser access, start the listener and copy its connection link. The listener binds only to `127.0.0.1`; the default link works on that computer. For another computer or phone, put an authenticated Harness session behind your private HTTPS proxy and set its public HTTPS origin in the same settings. The proxy must preserve the original Host and Authorization headers. Native provider setup and local microphone controls stay on the desktop.

The browser uses the same conversations and jobs. Closing its tab does not stop accepted work. Browser sessions persist on the runner; Disconnect revokes that session, Disconnect browsers revokes all sessions, and Reset connection link also replaces the shared key. The shared key leaves the visible URL after connection; per-tab access uses explicit authorization headers rather than cookies shared with other loopback ports. Desktop and simulated phone checks pass with fake inference. Remote-host deployment and real phone/network acceptance remain in progress.

Saved artifacts offer Download file or Download ZIP in the browser. A file must still match its published fingerprint; folders export their current contents, including assets and empty directories. Exports reject private files, links, active Harness writers and changed receipts. Downloads are limited to 512 MiB, 10,000 entries and two simultaneous snapshots or transfers. The browser streams through a single-use link that expires after one minute; that link grants access only to that prepared file. Logout and link reset cancel that session's transfers. The activity panel offers Stop downloads or Retry cleanup only when needed. Running a published executable remains an explicit Run on runner action; downloading never runs it.

## Voice input

On Windows, use the microphone beside the composer to dictate into your draft. Its tooltip shows the installed speech language. Send waits for the last recognized words; switching chats or hiding Harness stops dictation and keeps words in their original chat. Recordings stop after five minutes. Harness does not save microphone audio or use a transcription API. The button explains when local speech support is unavailable. Real microphone accuracy has not yet been checked.

Use **+** to attach text/code, images, PDF or DOCX files. Documents are read locally as text; chips identify that layout, images and annotations are excluded. Up to four items attach at once, with a 64 KB text limit and a 10 MB source limit per document. PDFs support up to 200 pages. Scans need page images; protected or oversized documents show an error without truncating content or discarding the current draft. Original documents are not copied into agent workspaces.

## Requirements

- Windows x64, or Linux x64/arm64 via `npm ci && npm start` (the `.cmd`/`.vbs` launchers are Windows-only)
- Node.js 22.13 or newer and Git
- At least one provider: Codex CLI (ChatGPT), Claude Code, Cursor CLI, another supported CLI, or an API provider (any OpenAI-compatible endpoint; no CLI needed)

No provider is required up front. Settings → Providers shows an **Install** button next to any CLI that is not detected, and an **Update** button next to an installed CLI with a newer official release (checked in the background at startup and on Renew; hover shows both versions). Either confirms, runs the vendor's official installer or updater for the newest release (npm `@latest` for Codex and DeepSeek Harness, claude.ai/install for Claude, cursor.com/install for Cursor, `agy update` for Antigravity, Muse's launcher), then re-detects it. Updating Codex stops Harness's Codex app-servers first, because Windows cannot replace a running binary, and reconnects them after. Sign in with the plug button afterwards. Configured task checks run in the Codex sandbox when Codex is connected; otherwise they run as local processes after an approval prompt that says so (Full access skips the prompt), with the same timeout, Stop and crash-recovery handling on Windows and Linux. The execution block is saved before a local check starts. When the check exits, everything it started is stopped and verified gone (Linux: an inherited `PHASMA_HARNESS_CHECK` environment tag; Windows: the process tree recorded while it runs, plus `ParentProcessId` links); a detached leftover is reported on the result, and an unverifiable one keeps the block. Descendants that clear their environment (Linux) or whose short-lived parent exited unseen (Windows) are not tracked. The context meter and manual compaction work for Codex and Claude sessions; Cursor reports no usage and has no compact command. The connected-MCP gateway and ChatGPT models need Codex, which is their runtime; OpenAI-compatible API providers run in Harness's own agent loop. Jev is optional and uses a key you save in Settings.

**Closing the window keeps work running.** Reopen Harness from its tray icon or launch it again to reconnect to the same runner. Settings → General offers optional start at sign-in. Pending approvals remain waits while the window is hidden. Choose **Quit runner** in the tray to stop execution and exit.

**Stop** ends a native CLI turn and its owned tool/MCP processes, including tracked descendants left behind after the CLI exits. Explicit Quit waits up to about 5 seconds for running work, then stops every owned worker tree; Codex gets 2 seconds to exit before forced cleanup. Windows tracks process ancestry and creation times; Linux uses the inherited `PHASMA_HARNESS_OWNER` tag. Leftovers are logged. New execution waits for cleanup, and Stop can cancel that wait. Unconfirmed cleanup blocks sends, queued messages, compaction and checks, persists across restart, and is retried every 15 seconds. Diagnostics shows the count. Crash recovery is still incomplete: Task Manager can bypass normal cleanup, and arbitrary uncertain side effects are never safe to replay automatically.

### Access by provider

The access setting applies to every provider; Codex enforces it with its OS sandbox, Claude and Cursor with Harness approval prompts. API providers follow the Claude rules in Harness's own agent loop: reads inside the workspace run; with Workspace access, edits inside it run too; commands and anything outside the workspace ask; Full access runs everything.

| | Codex | Claude Code | Cursor |
|---|---|---|---|
| Ask | read-only sandbox, no network; more asks | reads inside the workspace and read-only commands run; outside reads, other commands, edits and web ask. Small tool set, no subagents | permission requests ask |
| Workspace access | workspace-write sandbox, no network; more asks | reads, edits and filesystem commands inside the workspace run; other commands, outside edits and web ask | permission requests ask |
| Full access | no sandbox, no prompts | `bypassPermissions` | auto-approved |

Routing classifiers get no tools on any provider. An approval still open when a turn ends, is stopped, or is withdrawn by the CLI is declined. Claude's own `~/.claude` allow and deny rules still apply. Like Codex, each Claude model is offered at every effort it supports (`claude-cli:<model>:<effort>`), enabled per model in Settings → Providers, and the router picks the effort per task; a model without effort levels uses the CLI default. Cursor models get the same treatment from the reasoning levels (`thought_level`) Cursor lists in `cursor/list_available_models`; the chosen level is set with `session/set_config_option` (parameterized model picker), and Cursor saves the last model and level as its own default, as it already did for the model.

### Approvals, usage limits and diagnostics

- **Allow for this session.** An approval prompt can be answered once or for the rest of the session. Codex remembers it itself for that conversation (`acceptForSession`, or session scope for permission requests); Harness does not reset what Codex remembers when the access setting changes. For Claude and Cursor, Harness remembers the tool together with its exact target, never the tool as a whole: Claude's Bash, file, search and web tools by their command, file, pattern or URL, and any other tool (MCP tools, Task, …) only when its whole input repeats exactly; Cursor by the command, file or URL its request names, and MCP calls with their arguments. Requests without a specific target, plans and questions are never remembered, and changing the session's access setting or deleting the session forgets these answers.
- **Usage-limit failover.** When a provider reports that its plan limit is reached (Codex `usageLimitExceeded`/`rateLimitExceeded`, Claude's rate-limit result, Cursor's "Upgrade your plan"/"Add a payment method" reply), Harness marks that provider limited until its reported reset time (15 minutes when the provider gives none). Claude's weekly Opus or Sonnet window limits only that model family, and a rejected Claude window that paid extra usage still covers is not a limit. On Auto the same message is sent once more through another provider (or, for a model-family limit, another model of the same provider) that has an available model, with a notice in the chat; a manually chosen model only reports the limit, and so does a stopped turn or a paused queue. The refused attempt runs no task checks. While a provider is limited, Auto routing leaves out its models, and a limited routing model is replaced by another enabled one. A later successful turn with a model the limit covers clears the mark.
- **Usage limits in Settings → Providers.** A signed-in provider row shows "Usage limit reached · resets …" (or "Opus usage limit reached …") while that provider is limited. Plan usage percentages are not shown for any provider, since only Codex reports them reliably (Claude only near a limit and through an experimental request, Cursor not at all). Codex's windows are still read: a full one marks the limit ahead of time only without credits, since credits let usage continue.
- **API providers.** Settings → Providers → API providers adds an OpenAI-compatible endpoint (name, base URL, optional key). Keys are stored encrypted with the OS key store and are never shown again; each provider can be enabled, have its key replaced or cleared, or be removed. Their models appear in the Models list and run in Harness's own agent loop (chat completions with file, search, command and Harness agent tools), so they need neither Codex nor any other CLI.
- **Decision trace.** `logs/decisions.jsonl` in the data folder records, per worker turn, how it was routed (router or manual, model and effort, same task, switch, escalation, failover), what routing cost (calls, tokens, time, Jev cost), the worker's tokens for the whole turn (every model call in it; Cursor reports none) and time, the turn's status and the status the worker reported; and, separately, how a tracked message's configured checks ended. A reported "done" and passing checks are kept apart, and neither proves the task is correct. It holds no prompts, replies or documents, only models, counts, durations, statuses, references and hashes, and moves to `.1` past 1 MB.
- **Wiki check (log only).** Settings → Wiki → Check wiki updates with Jev (off by default, needs a Jev key). The wiki is read before an automatic wiki update and again after it. Each added paragraph of at most 600 characters that cites a `file:line` source is judged by Jev in two separate questions: does the cited source (the cited lines plus two lines around them, only from files Git tracks in the workspace, never dot-paths, private or credential files) support it (supported, partial, contradicted, insufficient), and against the most related passages of the wiki as it was before, is it covered, a new addition, a contradiction, or not durable project knowledge? Longer paragraphs, uncited ones and ones whose source cannot be found are logged as not assessable without a call; a verification date alone is not a source. Additions are batched (at most 8 per call and 24 KB of evidence, at most 5 calls per update; only that many additions are prepared, and the rest are logged as not assessed without reading their sources). Line endings are ignored, and a page rewritten beyond the diff limit is logged as changed too much. The comparison runs after the maintenance turn has finished, with bounded reads of the wiki folder. The verdicts, with references and hashes but no text, and each update's totals, including the check's own Jev calls, tokens, time and cost, go to the decision trace; Settings shows the counts. It never changes the wiki or what the maintenance turn does, and it does not make that writer safe. It adds no worker-model call, but the addition, the cited lines and the related passages are sent to Jev and billed by Jev.
- **Logs and diagnostics.** The app writes `logs/harness.log` in its data folder (rotated at 1 MB, two older files kept), with failed actions, provider disconnects, usage limits and crashes; keys and tokens are redacted. Settings → About → **Copy diagnostics** copies versions, provider states (no account emails), settings that affect routing, usage limits and the recent log, for bug reports. **Open logs folder** opens the folder. Prompts and replies are not logged.

Settings save as you change them; the footer **Close** only dismisses the window after pending changes finish. Check edits save when you leave a field, and removals save immediately. Invalid or failed check edits stay visible until corrected or removed.

## Run

```
npm ci
npm start
```

`Launch Phasma Harness.vbs` opens the app without a command window after dependencies are installed.

`Install Phasma Harness.cmd` installs missing Node.js LTS and Git through winget, runs `npm ci`, fetches the bundled tools, and creates a desktop shortcut. Before replacing dependencies, it requests a normal shutdown of this folder's Harness and waits for its workers and file locks to clear. If shutdown or file release takes more than 45 seconds, installation stops before changing dependencies and identifies the blocker; it never force-closes Cursor or unrelated apps. A Harness already running an older version needs one manual tray → Quit runner. Successful installation starts Harness again. Launching Harness normally while it runs brings back the existing window. Providers are installed from the app. Keep the folder where the shortcut points.

### Installer build and updates

`npm run dist` builds a Windows installer (`dist/Phasma-Harness-Setup-<version>.exe`) with electron-builder, pinned in the script and fetched by `npx`, so it is not a dependency of the source install. Build it on Windows after `npm ci`, because the bundled rg/rtk come from `tools/bin` for the build machine. The installer asks whether to install for you only (the default, no administrator rights) or for everyone on the computer, lets you choose the folder, and ships the app unpacked (no asar) because the provider CLIs run bundled files such as the helper MCP script, skills and `tools/bin` by path. It uses the shared Phasma icon and is not code-signed, so SmartScreen may warn on first run.

An installed app keeps everything in `%APPDATA%\Phasma Harness`, including Harness's per-workspace data (`Wikis`), so installing a newer version over it keeps settings, sessions and that data. A source folder keeps `Wikis` beside the app. An older `workspace-data` folder is renamed to `Wikis` once.

Updates: the installed app checks GitHub for a newer release about 10 seconds after it starts and then every 12 hours (a failed check is only logged), and Settings → About → **Check for updates** checks on demand. When one exists, a bar at the top of the window offers **Update and restart**. Nothing downloads or installs until you click it, and it is disabled while a turn or its checks run. It downloads that version's `Phasma-Harness-Setup-<version>.exe`, only from this repository's release downloads, keeps it only if its size and SHA-256 match what GitHub reports for the asset, then runs it silently (`--updated /S --force-run`) and quits; the installer replaces the app in place and starts the new version, keeping settings, sessions, logs and wikis. Downloads go to `%APPDATA%\Phasma Harness\updates` and are removed once they are no longer newer than the running version. A source folder only reports the new version and links to it.

To release: bump `version` in `package.json`, commit, and push a tag `v<version>`. CI then runs the tests, builds the installer and publishes it as a GitHub release (the tag must match the version).

### Bundled tools

RTK and ripgrep live in `tools/bin/` (Git-ignored). `npm ci` runs `tools/fetch.cjs`, which downloads the builds pinned in `tools/manifest.json` for Windows x64, Linux x64 or Linux arm64, verifies their SHA256, and skips tools already installed at the pinned hash. The app puts `tools/bin` first on `PATH` at startup, so every worker and helper uses these copies rather than system installs. To upgrade, change the version, URLs and hashes in the manifest and rerun `node tools/fetch.cjs`. Node, Git and the provider CLIs stay global: they are shared with the rest of the system and the CLIs hold your logins.

Sessions and settings are stored in `%APPDATA%\Phasma Harness`. The app uses your existing Codex, Claude, and Cursor logins. It does not copy those credentials. Each session store uses a JSON checkpoint plus an adjacent `.journal` file; preserve both when copying running-app data. Quit runner before backups or rollback. Normal shutdown checkpoints the journal into JSON.

## Tasks and checks

Worker messages are tracked automatically in the background. Direct Jev answers and wiki proposals remain untracked. Checks only run when configured; passing them does not establish complete task correctness. There are no task cards, acknowledgment buttons or per-message check controls.

Jev and Smart routing decide whether the configured workspace checks are useful for the current request, using their names and commands in the existing classification call. No extra model call is added. Relevant executable verification runs; unrelated checks can be skipped, with the decision retained in the internal task record. Manually selected models, which bypass routing, keep configured checks enabled . After a tracked turn, the app runs any retained checks configured under Settings → Checks. The task keeps the checks and access it started with. One failed run gets a single correction on the same model. A blocked or unknown check stops that correction. Stop during checks cancels the task. The correction sees the last 2,000 characters of each failed check's output (stdout, or stderr when stdout is empty). When that excerpt shows no error line but the full output has some (an early compiler error in a long log, or a Vulkan validation error only on stderr), up to six of them (at most 600 characters) are put in front, still within the 2,000 characters.

Workers give normal replies without a mandatory completion checklist. Check results and task evidence remain saved internally.

Main Bot chooses result handling in its existing dispatch call. Simple, self-contained tasks return the saved worker report directly, without another model call or duplicate reply. Complex assignments use one combined assessment-and-reply call per returned worker; the last batch response includes the other workers' results. Unmarked older assignments use this reviewed path. Configured build/test checks still run independently, and failed checks or workers cannot be labelled successful by an optimistic model reply. Automatic result returns do not trigger another call for reply suggestions. Normal chat suggestions remain available.

Model calls allow ongoing answer/reasoning output beyond two minutes, but stop after two minutes without such activity. Stop and configured budgets still cancel them. Providers that expose no intermediate activity still face that silence limit. Cursor reviews run with private deny settings; a detected tool attempt cancels the response and permits only the existing single format retry. If review fails, the worker's report stays available and Main Bot does not claim the request is complete.

The card also checks up to 20 explicit `file:line` or `file:start-end` citations from the latest final reply against current workspace files, reading at most 64 KiB per file. Paths outside the workspace (including symlink escapes), private paths, binary files, and files over the limit are not assessed. Resolved references only establish that the path and line range exist, not that the claim is correct. These signals never change check outcomes or trigger corrections. Other citation formats and historical file versions are not assessed.

### Wiki follow-up


After a worker completes and configured checks pass, Harness runs one internal wiki-maintenance turn on the same available model. It first assesses every original requirement and accepted amendment against current source and check evidence. Incomplete or ambiguous evidence means no edit. Only durable new knowledge belongs in the active wiki, with source references and verification dates; project instructions and source code are not changed. This is a model assessment, not a correctness guarantee. Failed, blocked, cancelled, unchecked and read-only tasks do not trigger maintenance. Existing access permissions and project validation rules still apply, including approval for an external wiki folder. Maintenance is hidden from chat, recorded on the task, and never replayed after interruption. It adds one worker turn per eligible task; no recursive tracking or automatic entry-file rewrites.

### Workspace wiki and Harness data

Settings → Wiki shows the workspace's own `docs/wiki` folder; Harness never creates or edits it, and Show in folder opens it when it exists. Agents change it only when you ask or when the project's own rules say so; the Propose button on a finished task asks that task's worker for a proposed update to review.

Harness keeps its own per-workspace data in the runner's data directory under `Wikis` (`%APPDATA%\Phasma Harness\Wikis`), one subfolder per workspace: lessons, rules on trial and kept (`kept-rules.md`), setups, comparisons, chat-scan notes and skill versions. The folder keeps its older name; wiki pages earlier builds stored there were imported once and are no longer read or searched.

With Local + Jev ranking, Jev scores each search excerpt in its own question, which names the excerpt by an ID key (E1, E2, …) rather than by its position in a list; paths and text stay in the data, never in the questions. `project_context` searches the workspace's `docs/wiki` alongside source, including a git-ignored wiki, with at most 200 wiki Markdown files and the existing excerpt/size limits. A wiki reached through a link is skipped. Other workspaces are excluded from source scans. Files stay local with no automatic publishing or synchronization; context excerpts still go to the chosen model/ranker as part of normal requests. Moving a project to a different absolute path gives its Harness data a new identity; automatic migration is not implemented.

Effort cap: next to Auto in the composer (and Settings → Routing) you choose how far Auto may go: up to low, medium, high (the default, and recommended), xhigh or max, which is marked with a warning because it is the slowest and most expensive level. Smart and Jev routing are only offered workers at or below the cap, so difficulty-based selection and usage-limit failover stay within it; a model with no level that low keeps its lowest, and models without effort levels are unaffected. A task that continues keeps its model at the highest effort still allowed. Manual model picks are never capped, and each routed turn records the cap in the decision log.

Jev is never required. When a Jev call fails (down, timed out, key refused), each feature uses its fallback: Jev routing hands the message to the Smart router, project search keeps local ranking, tool recommendations return the local candidates, and the wiki check logs the addition as not judged. Nothing retries a paid call. Settings → General → Jev then shows since when Jev has been unavailable and which of your settings are on a fallback; the next successful Jev answer clears it. Large tool output is always captured as excerpts; it is no longer a setting.

If a check's process cannot be confirmed stopped, every session refuses new work until that process identity is gone. Acknowledging the task does not lift that block. Restarting the app does not rerun an unfinished task.

Recovery requires confirmed process-tree termination or the measured parent-exit cleanup contract (Codex CLI 0.156.1 on Windows with full access, the version it was measured with). An unknown lookup or an unmeasured runtime does not establish that descendants stopped. It was measured on 2026-09-25 with the script below: after Codex exited, both when its input was closed and when it was terminated, none of a check's processes (including a detached one) were still running. Installs and updates now take the newest Codex, so re-measure a newer version before adding it to `MEASURED_REAP` in `src/tasks.cjs`; any other version relies on confirmed process-tree termination. `node tests/codex-reap-live.cjs [workspace]` measures it on Windows: it runs a check that starts a foreground and a detached process through Codex with full access, then ends Codex twice (closing its input, as the app does, and terminating it, as a crash does) and reports whether every check process stopped. It prints the exact `MEASURED_REAP` line to use only when both cases leave nothing running; it needs the Codex CLI but no login and makes no model calls.

### Validation

`npm test` runs every unit test (`tests/*.test.cjs`) with two test files at a time to bound native process fixtures; `node --test tests/tasks.test.cjs tests/core.test.cjs` runs just the task and controller regressions, and `node --test tests/bundled-tools.test.cjs` the tool manifest and large-response helper. `npm run smoke` opens the real window with a test controller (no logins or model calls) and exercises Settings and the chat UI; on Linux without a display use `xvfb-run -a npx electron --no-sandbox tests/ui-startup-smoke.cjs`. On Linux, `xvfb-run -a npx electron --no-sandbox tests/quit-live.cjs` starts the real app with fake Codex, Claude and Cursor programs (each with a child and a detached child), closes it with "Stop and close" while Stop fails, and checks that it still quits within its time limit and leaves none of their processes running (CI runs it). `tests/installer.test.ps1` checks the installer script on Windows without changing the machine.

CI (`.github/workflows/ci.yml`) runs the unit tests and the UI smoke on Windows and Linux for pushes to master and pull requests, plus the installer script test on Windows. The installer is built only for version tags or a manual run, to keep Actions minutes low.
Run `node tests/task-checks-live.cjs <workspace>` for an opt-in completion-gate smoke with a real Codex connection, temporary app state, and a read-only Git command. It makes no model calls and prints the retained evidence directory.
Append `workspace-write` to test Workspace access. The smoke approves only its fixed Git check; normal app checks still use the session's approval rules.

Measured 2026-09-23 in PhasmaEngine with Codex `0.155.0-alpha.16`, Windows, full access: three no-check gate runs took 349/480/401 ms; three Git-check gate runs took 1353/1071/1041 ms, including command times of 84/37/33 ms. Median gate times were 401 ms and 1071 ms. This is a small transport/persistence smoke, not an engine build, live worker, cancellation, or UI test.

Workspace-access follow-up on the same date/runtime: all three runs passed, at 2066/1979/2049 ms (median 2049 ms). Windows sandbox rejects a custom `outputBytesCap`, so checks use the server's default limit and still cap stored output locally. The latest task result appears below the conversation messages.

## Layout

- `src/controller.cjs` — sessions, sending and the worker turn; the rest of the Controller is split by area in `src/controller/` (`providers` catalog, routing models and usage limits; `turns` Codex turn events; `helpers` worker helper tools; `task-gate` tasks, checks and recovery; `shared` constants)
- `src/providers` — Codex, Claude, Cursor, and Jev
- `src/routing` — model choice and benchmark evidence
- `src/workspace` — project search
- `src/tools` — helper tools shared with those CLIs
- `ui` — the window
- `src/log.cjs`, `src/diagnostics.cjs`, `src/updates.cjs`, `src/updater.cjs` — log file, diagnostics text, update check and automatic update
- `benchmarks` — bundled measurements: only Artificial Analysis evaluations that cover every current model (Intelligence Index with price, speed and API cost per task, Terminal-Bench, SciCode, HLE, CritPt, AA-LCR, AA-Omniscience). Rows from dropped sources in an older saved or imported table are ignored. A context-size variant (Claude Code's `claude-opus-5-5[1m]`) shares its model's measurements, and a model the evaluator measured only with a provider fallback (Artificial Analysis's current Claude runs) reaches both routers and difficulty-based model selection with those runs, flagged, instead of with no numbers.

### Bundled default skills

Full SKILL.md files ship in skills/: caveman, ponytail, i-have-adhd, large-responses, workflow and rtk. The large-response Node helper and Ponytail license are included. No user-global skill directory is needed. Workers get a short defaults block (action-first replies, Ponytail full, workflow, output budget, bundled rtk/rg, wiki) plus an index of the skills with their paths, using each SKILL.md description when present. A worker reads a full skill only when its description applies, through `router_read_output` with `{"skill": "<name>"}` (works in every access mode and provider) or the file. Caveman is opt-in: listed, never active by default. The installer checks these payload files. Workspace overrides are resolved on each turn; adopting or undoing one needs no restart.

To compare a skill change, prepare a complete replacement folder in an ignored, untracked directory inside a Git project (add the folder to `.gitignore`), including `SKILL.md` and its scripts/resources, then ask Main Bot to compare that folder against the named Harness skill on a task with configured checks. For example: "Compare the workflow skill with `candidate-workflow/` while fixing the empty-name bug." Comparisons use the same descriptions and on-demand loading as ordinary turns. `router_read_output` returns editable source with frontmatter and `{{SKILL_DIR}}` intact, plus the directory for executing commands. The same comparison card shows the verdict and Undo. A change that helps is kept for this workspace in AppData beside its wiki, outside the installation. Other workspaces retain their own settings. Undo restores the prior revision identity, or removes the override so future bundled updates apply. Broken overrides fall back to bundled skills with a chat notice. Finished run snapshots are removed; Undo revisions follow the existing 50-comparison history, with expired actions labelled in chat. Skill folders may contain up to 256 files / 8 MiB, with a UTF-8 `SKILL.md` up to 64 KiB; links and special files are rejected. This compares existing Harness skills; it does not autonomously author or install new named skills. Harness automatic test-pool verification stays on its trusted bundled runner, and external CLI Stop hooks are not rewritten by skill adoption.

Skill comparison safeguards: candidate descriptions are limited to 300 characters, and older descriptions are capped in the always-on index. A body/resource change needs a recorded skill read in the changed run before it can be kept; description-only comparisons do not. Harness records helper reads and successful native tool reads whose reported output contains the skill body. If a CLI does not report enough evidence, the comparison stays inconclusive. Overrides remain active after bundled updates, with a notice to review them. Running turns keep their skill paths through Undo, and cleanup waits for workers to stop. Damaged comparison history is backed up and reconstructed from available chat cards with a visible notice; potentially referenced skill snapshots remain protected for the 50-comparison history window. Candidates can be excluded through `.git/info/exclude` as well as `.gitignore`.

### Routing cost

**Conversation reuse and caching.** Headless CLI execution does not mean a new conversation. Workers resume their provider session; Main Bot now also retains compatible Codex, Claude, Cursor and DeepSeek conversations. Main's saved continuation survives restart where the CLI supports durable resume. Older DeepSeek versions can reuse their running host but must support native resume to recover it after restart. Changes to model, instructions or edited/cleared history invalidate Main's continuation. An uncertain failed call is not replayed automatically.

Main sends conversation changes instead of rebuilding a growing transcript in each prompt. Cursor and other native workers receive unchanged instruction text once per session; edits refresh it. Codex avoids reinjecting unchanged instructions on reload. Group members get new shared messages as conversation data, with stable instructions and separate private sessions. Claude and API workers retain their stable system prefix on each request. API histories preserve reasoning/tool messages needed for continuation and caching; supported endpoints receive documented cache-affinity hints, with explicit caching enabled for supported OpenRouter models. Unknown endpoints receive no guessed vendor options.

Provider caching is best effort, not free context or guaranteed savings. Stateless APIs still transmit history; cache hits can reduce its processing cost. Eviction, model changes, compaction and instruction changes can cause misses. Harness keeps missing usage unknown, counts schema-repair calls, and marks incomplete tool-loop totals. A fixed-model plain reply needs one inference call, but Auto routing, tool use, context summaries, configured reviews and enabled improvement features can add calls. Reply suggestions and automatic chat scans retain their existing user-controlled settings; this optimization does not switch them off. Regression tests: `tests/prompt-cache.test.cjs` and test-pool `provider-prompt-cache`. Account-backed checks are explicitly opt-in: `node tests/prompt-cache-live.cjs --run codex cursor-cli`.

Group progress messages do not consume shared-context slots, and unchanged group instructions are not repeated with new messages. Schema-repair notes remain conversation messages so a successful retry does not invalidate the next normal turn. A missing or damaged API transcript can recover from Harness history before any request is sent; uncertain provider failures still require a retry. Codex refreshes worker instructions once after manual or observed automatic compaction, when the active turn has settled. Reopening a chat or invalidating its settings cannot reload an active turn.

Persistent Main transcripts live in the native provider's store. Once per day of use, Harness removes unused Codex/Claude Main transcripts older than 30 days from its dedicated router workspace, while protecting active Harness chat references. Codex pinned or running threads, uncertain Claude records and unrelated workspaces are preserved. Cleanup makes no model calls; unsupported or failed cleanup is logged and retried on a later day. Harness chat history is retained independently.

On Auto, every message is routed from the full catalog, so a session that starts with a simple question can still move to a stronger model for review or debugging. Task tracking is enabled independently unless skipped for that message. The router is told which worker already holds the conversation (`currentWorker`) and keeps it when adequate, because switching makes the next worker re-read the conversation without the prompt cache once; it switches for a different capability need or a clearly cheaper adequate choice, not back and forth. The router sees a compact catalog: one flat row per worker with only routing-relevant numbers (general index, repository engineering, coding agent, terminal, tool use, algorithmic, long context, instruction following, API price, speed), each from one comparable benchmark version and harness, with assisted fallback runs excluded. Its fixed prompt is about 750 tokens instead of about 3,100. Jev ranking keeps the full benchmark view.

**One model per task.** Workers end each final reply with a status line, `[task: done]`, `[task: pending]` or `[task: needs-input]` (also read when a model formats it or adds a short closing line); the Harness reads and hides it, shows a small "Task pending" or "Needs your input" tag on unfinished work, and keeps it out of router context, handoffs and wiki proposals. The session remembers its current task: the request that started it, the worker running it and that status. With every Auto prompt the router (Smart or Jev, in the call it already makes) sees the current task and decides whether the prompt continues it ("fix that", "we need more of this", an answer to the worker's question) or starts a new one. A continued task keeps its worker and effort, and skips the workspace scan and second routing call; the reason says "Same task: kept …" and names the model the message would get on its own when that differs, so a task that outgrew its model is visible. A new task is routed normally. A manual model choice continues a task its worker reported as pending or waiting for input, and becomes its worker (otherwise it starts a new task); a worker that is disabled or at a usage limit is replaced by the router's pick. Corrections and checks stay on the task's worker. The per-message task records used for checks are unchanged.

**Difficulty determines reasoning.** Both routers assess Low, Medium, High or Xhigh difficulty from task scope, separately from write risk, missing evidence and confidence. Low/Medium work retains the router's economical model choice with effort matched to difficulty. High/Xhigh work uses the strongest measured model across all offered providers, with effort matched to difficulty within the cap. There are no model-name rules. Unknown benchmarks retain the selected model; unsupported effort levels use the next offered level or the highest offered level when capped. Low confidence alone cannot promote a bounded explanation, and high confidence cannot leave a difficult task at low effort. The difficulty and any adjustment appear in the route and decision log. Continued tasks retain their worker; Hub keeps its separate balanced chat-model policy.

Smart first classifies the request without scanning the workspace. Only when that decision needs workspace evidence does it scan and make a second call. Successful two-call routes sum both usages; general requests have no discarded background classifier. This saves calls on general requests, but makes workspace-dependent routing sequential and potentially slower. See [measured routing results](benchmarks/results/routing-demand.md).

**Compare with Jev** (Settings → Routing, shown with a saved Jev key while Smart routes; off by default) is log only. After each message is routed, Jev is also asked in the background, the way Jev routing would ask, which model it would pick, and its pick is logged next to the model that actually ran, whether the router or you chose it. Routing, the worker and its token use do not change; each compared message is sent to Jev and billed by Jev. The log (`logs/jev-compare.jsonl` in the data folder) keeps the chosen models and Jev's cost, never message text, and Settings shows how often Jev agreed. One comparison runs at a time; a message sent while one is still running is not compared. Use it to judge Jev routing on your own work before switching the router to Jev.

Codex receives developer instructions; Claude an appended system prompt; Cursor a prompt prefix. Classifiers and Jev yes/no shortcuts stay unchanged. User style overrides remain supported through conversation instructions. These instructions are not enforced guarantees.

The installer provisions Node and Git when absent or unusable, and fetches RTK and ripgrep into `tools/bin`. Provider CLIs are installed on demand from Settings → Providers. Python is not required. Working installations are preserved. Bundled skill files are checked before installation. Downloads for Cursor, npm and Electron are kept in installers/; WinGet manages other package downloads. WinGet must already be available. This is not a complete offline installer. See skills/README.md.

### Project rules and memory

Project rules live in the workspace's own root `AGENTS.md`; make `CLAUDE.md` and `GEMINI.md` one-line `@AGENTS.md` imports so every tool reads the same file. Harness never creates, edits or consolidates these files, and the installer preserves its own AppData on uninstall (`deleteAppDataOnUninstall: false`). Back up both; this does not protect against manual deletion or disk loss.

Bots load the rules the way they do outside Harness: Codex, Cursor, Antigravity and the DeepSeek CLI read `AGENTS.md` themselves, and Claude Code reads `CLAUDE.md` (and `AGENTS.md` through the import); Harness no longer hides these files from them. Harness passes the root `AGENTS.md` itself only where that does not happen: Muse (which skips it in workspaces it does not trust), API models, Claude in a workspace without a `CLAUDE.md`, and Harness's own routing calls. It is reread before each turn; one over 64 KiB is not passed (the bot is told where to read it), and Codex silently truncates past 32 KiB, its default `project_doc_max_bytes`. Codex threads and Cursor's reused sessions may keep the `AGENTS.md` they loaded until a new chat. Isolated jobs copy the root rule files into their frozen copy. Subfolder rule files load only as each tool loads them on its own. Instructions do not restrict filesystem permissions.

Rules Harness learns (a trial rule that held up, a compared rule that helped) stay on Harness's side in `kept-rules.md` and are passed with every turn in that workspace; each one's chat line has an Undo, and deleting a line by hand removes the rule. A compared project rule reaches only the changed run, from Harness, so no file in either copy differs. Harness runs no wiki turns by itself.

Until 2026-10-25 Harness created a `PhasmaHarness.md` entry in each workspace and injected it instead. An old entry is now inert and can be deleted once its rules are in `AGENTS.md`; Apply never copies one back from a project copy.

Opt-in live verification: `node tests/project-instructions-live.cjs "<absolute Harness data (Wikis) folder>" [provider ...]` uses real accounts and inference. It checks fresh codes from the workspace `AGENTS.md` (which `CLAUDE.md` imports) and `docs/wiki`, then changes both and checks the same chat again. Antigravity requires the explicit `--allow-full-access` test option. `--git-ignored` makes the rule files and wiki local-only first. On 2026-10-25 Claude and the DeepSeek CLI passed both turns; Codex and Cursor passed the first and, in the same chat, kept the first turn's `AGENTS.md` code while reading the new wiki code.

Memory consists of the workspace's rule files and wiki, retrieved on demand via project_context, plus saved session history and Harness's learned rules and lessons. Persistence does not guarantee the model retrieved every relevant fact; there is no automatic learning from every conversation.

Claude model discovery uses the signed-in CLI initialization response, without an inference request. Providers and routing use its versioned model IDs, deduplicating aliases while retaining context variants. Renew refreshes this list; discovery errors never fall back to hard-coded Haiku/Sonnet/Opus presets.

### Maintenance checks

Run `npm run check` for strict JavaScript type checking of the extracted session store, shared agent-state rules, report parser and provider contracts, then `npm test`. CI runs both. The remaining orchestration code is not yet type-checked.

`npm run check:providers` checks the installed provider CLIs without inference or sign-in. Missing optional CLIs are reported as skipped; pass required names, such as `npm run check:providers -- codex claude`, to require them. The weekly **Provider compatibility** workflow installs current Codex and Claude releases, checks their interfaces, exercises real Codex/MCP against a local Responses fixture, and runs adapter regressions. No model credentials or paid requests are used. Help checks detect interface drift; they do not verify live model behavior or account quotas.
