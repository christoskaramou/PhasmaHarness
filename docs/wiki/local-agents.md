- **Document worker memory (R5, fixed 2026-10-19).** pdf.js typed arrays and canvas pixels live outside the worker's 192 MB V8 heap, so each reader process now gets an OS cap of 768 MiB committed memory. Only the worker is capped, never the runner, providers or game builds.
  - Windows: one long-lived `src/document-job.ps1` per `DocumentReader` holds a private job object with `JOB_OBJECT_LIMIT_PROCESS_MEMORY | KILL_ON_JOB_CLOSE`. It nests under the runner job and libuv's job (Windows 8+). The worker is forked, its PID is assigned and checked with `IsProcessInJob`, and only then are the bytes sent. While the PID is with the helper the worker is never killed, so the helper cannot open a reused PID. The helper starts once in about 0.4 s; each assignment takes about 10 ms.
  - Linux: the worker is forked through `/usr/bin/prlimit --data=<cap> -- node …`. prlimit execs node, so the IPC channel and environment survive. `--as` would break V8's address-space reservations. A service `MemoryMax=` would cap builds and providers too, and `systemd-run --scope` would leave the service cgroup, so neither is used.
  - macOS has no cap.
  - If the cap cannot be applied (no helper, assignment failed, no prlimit), the file is not read.

In WSL Ubuntu the worker starts at about 50–70 MB `VmData`, and 640 MB of buffers fit before the cap.

Node 24's disconnect only waits for queued handles, so it closes the channel on the next tick and cancels a write still waiting on the pipe buffer. The worker exits 0 and the parent gets no message. Node's async IPC write callback reports success even when the write was cancelled.

## Built-in Phasma game checks

Built 2026-10-20 for the game-verification gate. `src/phasma-game-checks.cjs` is both the recipe and the checker it runs.

- **Offered when:** on Windows, the workspace has `runtime/PhasmaPlayer.exe` and `runtime/minilua.exe`, and `runtime/phasma_settings.json` points that Player at this workspace's `phasma_project.json` (`project_manifest`, or `project_path` plus the default manifest). Resolution follows the engine's `ProjectSelection.cpp`: paths are relative to `runtime/`, and the manifest's `assets` field is relative to the project. `assetsRoot()` returns null when the Player would open some other project. This is the layout Harness game batches use (`.scratch/phasma-acceptance-prep.cjs`). The game itself need not exist yet, since workers write it. PhasmaProjects games that run the engine's shared Player (`run.ps1`) are not covered.
- **Offered how:** Settings → Checks shows "Add Phasma game checks" for such a workspace (IPC `phasmaGameChecks`, host only, never on browser access). It adds three ordinary checks through the normal save path, never automatically, and is not offered again once they are saved.
- **Commands:** `[process.execPath, <src/phasma-game-checks.cjs>, build|launch|gameplay]`, with timeouts of 30/90/120 s. These are absolute paths: moving the install or checkout breaks them loudly ("was not found"). How `task-gate.cjs` runs a check whose `argv[0]` is Harness's own executable:
  - It always runs it locally (`runCheck`), because Codex `command/exec` takes no environment. Under workspace-write access, that means the honest "without the Codex sandbox" approval prompt.
  - It sets `ELECTRON_RUN_AS_NODE=1`, so a packaged app never starts a second instance. That second instance would quit with exit 0 and falsely pass the check.
  - It passes `HARNESS_CHECK_TIMEOUT_MS`. The checker stops 15 s before that timeout, so it can stop the Player and clean up, even if the user edits the timeout.
- **Build:** compiles every `<assets>/Scripts/**/*.lua` with `runtime/minilua.exe`. The file list goes through a list file, not the command line. Shortcut: minilua is plain Lua 5.1, so LuaJIT-only syntax (`goto`, labels) fails falsely. Gamekit has none (checked 2026-10-20).
- **Launch:** starts the Player and waits for live frames over its MCP server. `game_describe` must report protocol 1 and a game id. When `<assets>/game.json` exists (batch games write one), its `gameId` must match.
- **Gameplay:** generic gamekit play (`verifyGameplay`, `driver.lua` semantics):
  - the game starts unfinished with legal actions, from a reset or, when `reset_supported` is false, from an observe;
  - up to 50 first-legal-action moves, each in the same session with a higher `state_id`, waiting out `busy`;
  - a reset (when supported) starts a new session;
  - an action against the first state is rejected `stale_state` and changes neither the session nor the game. For `state_tracking: game_epoch` games, a stable `state_id` counts as unchanged, since their view keeps moving. Other games must keep the same observation.
  - a PNG screenshot is taken.
  Game rules (solving a board) belong to the game's own tests.
- **MCP opt-in:** the Player starts MCP (which runs any Lua) only from `<assets>/Agent/agent_config.json` (`PlayerHost.cpp` `ReadPlayerMcpPort`; no CLI or environment switch, checked 2026-10-20). The checker backs that file up to `runtime/harness-checks/agent_config.backup.json`, opts in on a free port, and restores it afterwards. Harness also calls `restoreMcpOptIn` after every recipe check whose process tree is confirmed gone, so a Stop or timeout that hard-kills the checker still restores it. A Harness crash mid-check leaves the opt-in until the next recipe run, which restores it first. Shortcut: two recipe checks running at once on the same workspace can race on the backup; batches give each job its own copy.
- **Evidence:** one JSON line on stdout, kept by the check result. Scratch files and `gameplay.png` stay in `runtime/harness-checks/`, out of the game's source.

## Setup fingerprint

Built 2026-10-20 (harness2 item 1 in the plan). `src/setup-fingerprint.cjs`: what shaped a worker run, as readable parts plus `hash` (16 hex of SHA-256 over canonical JSON with sorted keys). It makes no model calls and starts no processes.
- **Parts (`v: 1`):**
  - `harness` version;
  - `provider`, `providerVersion` (cached only: Codex `client.version`, native CLI `status.version`; null for Claude, Cursor and API providers), `model`, `effort`, `access`;

- **Saved on:**
  - each worker route (`Controller.runSetup`, in the Codex `turn/start` path and `sendCLI`);
  - the task attempt of that turn (`runGate`);
  - each delivered `agentResult` item: the last route with a setup, so after a failover it is the provider that finished.

## Routines

Assigned input boundary (verified 2026-10-18): when a live delegated worker cannot read its originating chat because that chat is Full-access or in a different workspace, `Agents.readContext` exposes only the request already assigned to that worker. The response is explicitly labelled `assignment-input`; unrelated source messages, logs and history remain private. The exception ends with the assignment and does not permit other Full-access conversations or filesystem reads. Covered by "a restricted worker can retrieve its long assigned input…" (a plain delegation since 2026-10-20) and existing context-access tests in `tests/coordinator.test.cjs` and `tests/agents.test.cjs`.

Redesigned 2026-10-20 at the user's request ("use text to ask the agent again at a specific time"; verified by tests, no live firing yet): a routine is saved text that Harness sends back to an agent, as a new message in the chat where it was saved, on a schedule, once at a date and time, or on each new local Git commit. One-time routines (added 2026-10-20 at the user's request): trigger `once` with `date` (YYYY-MM-DD), `time` and `timeZone`; `routine-time.once` validates a real date, refuses a local time skipped by a spring clock change and runs a repeated autumn time at its first instant; saving refuses a time that is not in the future; after its run settles, `refreshRun` deletes the record. A one-time run missed while Harness was closed fires once when Harness next checks. Tests: `tests/routine-time.test.cjs` "one-time routines run at a real local date…" and `tests/coordinator.test.cjs` "a one-time routine runs once…" (fails without the self-removal). Records are schema 2 in the primary store (`data.routines`): `agentId` (the agent it runs on; `main` for Hub), `ownerId` (that chat; Clear moves it), `createdBy`, `name` (defaults to the start of `text`), `text`, `schedule`, `access`, `workspace`, `next`/`head`, `enabled`/`error`, `run` and `last`. When due, `Routines.fire` calls the agent's ordinary `send` with a `routineRun` marker, so the message queues behind a busy turn like a typed one; the marker is carried through the queue, failover resend, pending message, committed chat item and Hub's message, and the UI labels it "Routine · <name>". A run lasts while its message is queued or its turn runs (`live`), and the next occurrence waits for it, including across a restart. An agent that is not ready (connecting, blocked, busy in another chat, queue full) keeps the occurrence for a later tick. A run is held (disabled with an error) when its chat's access is now higher than the access approved at save, or a Git routine's chat moved to another folder; saving or resuming from chat re-approves at the lower of the routine chat's and the asking chat's access. A failed run is recorded in `last.error`, not held. Ownership rule (chosen 2026-10-20): a routine dies with the agent it runs on, so routines saved in Hub (main or group chats) persist and Hub can delegate when one fires, while a bot's own routines are deleted with the bot inside `deleteAgent`'s save (rolled back if that save fails).

`src/routine-time.cjs` computes timezone-aware local times and weekdays with Intl data. Spring gaps are skipped; only the first instant of an autumn fold is eligible. Calendar misses coalesce into one admitted occurrence and advance from the current clock. Local Git HEAD triggers capture their initial baseline before acknowledgment and poll at up to 30-second intervals, sharing one read per workspace in a cycle. J5 (user decision, verified 2026-10-19): when a Git routine's run settles (its message left the queue and its turn ended), the HEAD at that moment becomes the new baseline, so the run's own commits never start it again. Any commit made before the settle, the user's own included, is absorbed; only later commits trigger. `refreshRun` saves `rebaseHead` with the finished run (restart-safe), the next cycle reads HEAD without waiting for the 30 s poll, and `save()` (edit/Resume) clears the flag because it reads a fresh HEAD itself. Regression: "a Git routine takes the commit its finished run left as the new baseline…" in `tests/coordinator.test.cjs` (fails without the fix). Git reads use fixed argv, no shell, a five-second timeout and owned cancellation. A paused, edited or closed routine cannot admit a stale async read. An empty scheduler has no timer. Future enabled routines alone do not block updates; active admission and Git reads do. Explicit runner shutdown aborts and waits for owned reads; hiding the window leaves the runner timer intact.

Chat-only control (2026-10-20): the tools `routine` (save, pause, resume, delete; omit `id` to create) and `routines_report` live in `src/tools/agent-tools.cjs`, so Hub and every bot get them; `Agents.tool` routes both to `Routines`. Hub sees and changes every routine; a bot sees and changes only its own. Changes are allowed only in a turn the user typed in that agent's own chat: `send` sets `session.userTurn` only when the message is not an automatic result or mail, a routine run or a wiki proposal; the task gate's correction and wiki-maintenance turns (which start through `submitWorker`, not `send`, and carry check output or wiki content) clear it; `Routines.userTurn` also refuses assignment execution contexts and `session.delegation`. The report is allowed everywhere. `tests/core.test.cjs` "one failed check corrects once…" asserts the correction turn is unmarked. `routines_report` returns id, agent name, name, text (600 chars), trigger in words, next run, state and last run; Hub's per-turn context no longer carries routines (it calls the report for ids). There is no routine UI or IPC: the dialog, `ui/routines.js`, the Options button, the status row, the Repeat button on results, `routineSave`/`routineChange` (preload, runner, phone remote) and the `routines` snapshot field were removed, and the runner's `send` strips any `routineRun` a renderer passes. The decision is saved before the job is queued, and the existing attempt counter still prevents a second automatic start after another crash.
- Work that may have run (`uncertain`) has no rerun path. Jobs saved by an uncontained or older runner only offer Return.
- `restartRecovery` keeps the first restart's record until the job resumes. A later restart of resumed work records that run as uncertain instead of keeping a stale "not started".

At most 50 records per project; a lesson unseen for 90 days expires, except the newest 10, so a project left alone for months keeps its latest ones (`fresh`, applied on read and write).
- **Where:** `lessons.json` plus a generated `lessons.md` in the project's wiki root (`WikiStore`, Harness-managed or the user's chosen folder). Batch copies are keyed to their source project (`lessonWorkspace`).
- **Use:** `openTask` attaches `task.lessonBlock` for a new task (not `[Router]` corrections): up to 3 lessons sharing words with the request or concerning a check that will run again, within 1,500 characters, framed as quoted check output. `withTaskLessons` in `src/controller.cjs` puts the block in front of that task's first worker message on both turn paths (Codex `turn/start`, CLI/API `sendCLI`). - **Regressions:** `tests/lessons.test.cjs`, "a corrected check failure becomes a lesson…" in `tests/core.test.cjs`, pool entry `task-lessons`.

Richer records (2026-10-20, harness2 item 2; fixtures only, no model calls). Each new record also has these fields:
- **`situation`:** the failing checks, the first error line, and the failing attempt's setup hash, provider and model (from the setup fingerprint).
- **`change`:**
  - the files whose stat line changed, each with its `git diff --stat` text;
  - `setupChanged`: whether provider, model, effort, access, instructions, skills, tools or checks differ between the failing and final attempts. Lessons are not compared, since only a task's first run carries them; attempts without a setup count as unknown, not changed;
  - `amended`: whether the assignment was amended in between. Attempts now save the amendment count (`runGate`). Older attempts have none, so any amendment on the task counts.
- **`evidence`:** the checks passing and failing after the correction, plus regressions. A regression is a check that passed before and fails after; a check that did not run says nothing.
- **`verdict`** (harness2's four) judges this task's correction, not whether offering the lesson helps later tasks; that needs the two-run comparison (item 3):
  - **hurt:** a regression;
  - **confounded:** the setup or assignment also changed, or a different error remains;
  - **helped:** the checks were fixed;
  - **no observed effect:** the same error repeats.
- **`confidence`:**
  - **high:** helped at least twice (the per-record `verdicts` counts survive merges);
  - **medium:** helped once with a known code change;
  - **low:** helped without a visible change (plain folders have no git diff), and every other verdict.
- **No record** when the failure has neither output nor an exit code (thin evidence). A fix whose stat lines look unchanged is still recorded.
- **Offering:** confounded records are kept on the page but not offered (a guess, as harness2 puts it). Records from before verdicts are still offered and show only their outcome. The offered line ends with "· verdict, confidence".
- **Tests:** four tests in `tests/lessons.test.cjs` cover the verdicts, thin evidence, merges and old records. The gate test "a corrected check failure becomes a lesson…" (`tests/core.test.cjs`) asserts the new fields through the real task gate: per-attempt setup and amendment count, `situation`, verdict helped, and the verdict in the offered line.

## Two-run comparison

Built 2026-10-20 (harness2 item 3; design approved by the user that day: instructions now, skills later; one pair by default, up to three on request; 20% threshold; blind pick optional).
- **Start (automatic since 2026-10-21):** only the Hub has the `compare` tool (`COMPARE` in `src/controller/coordinator.cjs`); workers never get it, so a comparison cannot start another. The request is the approval: `compareTool` plans and starts at once, with no confirmation turn. `planComparison` (`src/controller/comparison.cjs`) refuses a project without configured checks, a second running comparison in the same project (one older than a day stops blocking), and too many jobs. Without a named model, `comparisonMode` calls the router once for the request and pins its choice for every run, so the runs never differ in model. Spending is bounded by the existing background usage limit: comparison runs are ordinary delegated jobs and pass through `backgroundQuota` in `pump`.
- **Runs:** `startComparison` computes the lesson block once, plans the pairs (`planRuns`: labels A/B, which one carries the change is random per pair) and dispatches one batch of 2 × pairs workers named "Compare N" from one snapshot, with the pinned mode. Workers get only the task text: the user's compare message names the change, so neither the verbatim request nor the `agent_read_context` pointer is passed on.
- **The change:**
  - `bot`: the changed run's worker instructions get the change appended (`coordinatorTool`).
  - `project`: `prepareCopy` (called from `pump` in `src/agents.cjs` once a copy is ready, before its checks are mapped) writes the snapshot's `PhasmaHarness.md`, or the starter when there is none, into every copy, and the base plus the change into the changed run's copy. `git update-index --skip-worktree` hides the edit from `git diff`, so the diffs shown do not tell the runs apart.
- **Kept identical:** the copy record carries `comparisonId`, and `comparisonOf(session)` gates the task gate while the comparison runs:
  - `openTask` uses the frozen lesson block;
  - `saveLesson` records nothing;
  - `maintainWiki` does not run;
  - `runGate` restores check files from the batch input snapshot after capturing the diff and before the checks run (`restoreCheckFiles`; saved per attempt as `restored`). Only files named in a check command are protected; a test runner's own suite (`npm test`) is not.
- **Results:** a returned run skips the Hub's completion check and follow-ups, which would give one run extra turns. `collectComparison` measures it from the delivered result item (`runResult`): check statuses, corrections, every attempt's setup (`deliver` adds `corrections` and `attempts` for comparison jobs), complete tokens, dollars only when complete, active time. No model call.
- **Verdict per pair (`pairVerdict`):**
  - **confounded:** a run not completed, checks that did not run cleanly, a setup that changed between attempts (lessons ignored, since corrections run without them), first-attempt setups that differ beyond the changed instructions, or a change that did not reach its run;

  - then fewer corrections is **helped** (more corrections is no observed effect, as designed);
  - then tokens: at least 20% fewer is **cheaper**, not helped, since cost says nothing about quality; anything else is no observed effect. Active time decides only when either run did not report its tokens completely; it is noisier (provider load, network, check duration). Chosen by the user on 2026-10-20 after the live run below.
- **Overall (`overallVerdict`):** a strict majority of the comparable pairs; one pair, a split or any confounded pair is low confidence, two agreeing pairs medium, three high.

- **When:** `send` calls `scanAfterUserTurn` for a real user turn (`session.userTurn`), never for `[Router]` corrections, failover re-sends, delegated jobs or comparison runs. The exchange is taken at once, before the new message opens its own task, and scanned on the next tick; the hook never throws or delays the send. Worker chat: the last task's items from `startIndex`. Bot chat: the last real request plus the run of the one job it delegated (`agentResult` items, worker task by `assignmentId`, project = the result's workspace); no job or several jobs are skipped.
- **Scan:** the chat checker (`chatScanner`): Settings > General > Chat checker model, any enabled model that answers in a schema (`chatScanChoices`, snapshot `chatScanPresets`, setting `chatScanModel`, added 2026-10-21 at the user's request); **Off by default** (no `chatScanModel`, or `off`): the user picks the model by hand, and only that model checks; while it is unavailable nothing is scanned. There is no Auto and no Jev option (decided 2026-10-21: the user judged Jev unfit for checking; it can only pick among options, so it could not quote the exchange). Changing it never waits for agents to stop. Within the background usage limit, once per exchange (`claimScan`, before the call, so a failure is not retried). Shown, redacted: the request, the newest work that fits (6,000 characters), the task's outcome, the user's next message, the project's `PhasmaHarness.md` and riding rules, and the chat rules the task carried. Answer: `worthy`, `problem`, a verbatim `moment` (no quote, not worthy), per carried chat rule `recurred` / `avoided` / `not relevant`, and `outcome` (accepted / corrected / unclear), which decides proven setups for tasks without checks (see Proven setups).
- **Escalation:** a worthy exchange goes to `strongestPreset` (best measured worker that answers in a schema, medium effort; without measured scores the router's model), at most 5 calls per project per day, counted when made (`claimEscalation`). It answers `rule`, `note` or `nothing` through the reflection guard. A rule goes on trial with `check: null`, `error` = the problem, `goal` = the request, `source` = "the chat" (retired text refused); a note joins `notes.json` (30 at most, older than 90 days expire except the newest 10). Each posts a notice with Undo (`trialStarted`, `noteAdded`).
- **Chat rules on trial:** carried only by tasks sharing two words with the request they came from (`chatMatches`), one per task, so they never ride everything. `recordOutcomes` leaves them alone (no check to decide them); the scanner's verdict at the next exchange does (`recordChatVerdicts`): recurred = hit (dropped, or rolled back once kept), avoided = clean (three keep it), not relevant = none. Kept chat rules count as carried from `PhasmaHarness.md` only on a close match, which also stamps `lastMatchedAt`.
- **Notes:** offered to tasks sharing two words with the note or its request, at most 2, as context after the rules ("Notes Harness took from earlier chats…"). `notes.md` lists them.
- **Tests:** `tests/chat-scan.test.cjs` (redaction, grounding, verdict filtering, escalation guard, once per exchange, 5 a day, notes, Bot attribution, never scanned cases); `tests/trials.test.cjs` (two-word matching, one chat rule per task, checks never decide them, verdicts keep/drop/roll back); gate tests "a correction in the chat becomes a trial rule…" and "a note from the chat rides matching tasks…" (`tests/core.test.cjs`); UI smoke step "rule notices".

## Apply a project copy's changes

Built 2026-10-21 (first half of "suggested comparisons", requested by the user so a comparison or batch run's result can reach the real project; tests and smoke only, no live run yet):
- **Where:** a finished comparison applies its better run by itself (see Two-run comparison). By hand: an "Apply changes to my project…" button in job details (once the job is delivered; choosing among several batch copies stays the user's call) and an Apply button per run on a comparison card when nothing landed by itself. Both call the `applyCopy` runner command, which is also on Remote Control.
- **What counts as a change (`JobWorkspaces.changes`):** the copy's current files (`inventory`, so ignore rules apply) against its batch snapshot manifest (`input.json`, content hashes of every working file, git and plain folders alike). So a file that was already dirty at snapshot time is not a change, and ignored build outputs are never applied. Left out: the copied external wiki (`.phasma-job-wiki/`), an added `PhasmaHarness.md` equal to the starter Harness writes into every writable workspace, and `PhasmaHarness.md` in a comparison copy (a comparison's rule is adopted separately).
- **Conflicts:** a change applies only where the project's file still equals the snapshot (or is absent for an addition). Any other difference refuses the whole apply and names the files. A file the project already has with the copy's content is skipped. A different project file edited since the snapshot is no conflict.
- **Safety:**
  - the dialog lists up to 30 files and says the changes land uncommitted (nothing staged or committed), that ignored files are not applied, and where the previous versions stay (the batch snapshot's `input` folder);
  - `apply` re-runs the preview after the dialog and writes nothing unless it matches exactly;
  - each file is checked again just before its own write; deletions go first (a case-only rename is one file on Windows);
  - writes go to a temp file renamed into place;
  - paths follow `scoped()`'s rules (`resolveInside`), and an existing link on the way is refused;
  - refused while a bot still works in the copy (an undelivered job with this copy or scope, or a running chat turn there).
- **Target:** the snapshot's `source`, checked against the copy record; a copy of a copy applies into its parent copy.
- **Tests:** four "Apply …" tests in `tests/job-workspaces.test.cjs` (git and plain folder: edits, additions in new folders, deletions, rerun finds nothing, dirty and ignored files left out, conflicts, identical additions, Harness files, busy copy, copy changed after preview, a junction in the project); "Apply shows the files…" in `tests/runner-commands.test.cjs` (dialog text, 30-file cap, Cancel and conflicts write nothing, exactly the preview is applied); the UI smoke checks the job-details button (hidden while running) and the card's Apply buttons (only after reveal).

## Local model memory and context

Verified 2026-10-10. `src/providers/local-models.cjs` discovers model-management APIs at the configured provider endpoint (preserving reverse-proxy prefixes and authentication). LM Studio supports load/unload and context sizing; Ollama uses a Harness-named preset derived from the downloaded model with `num_ctx` set, because OpenAI-compatible requests do not retain a one-off native context override. These small preset definitions reuse weights; the original model is unchanged. llama.cpp router mode supports load/unload, but context size is server configuration. Unsupported endpoints and hosted providers keep their existing inference path. No model downloads are started.

Workers and the routing classifier prepare local models before inference. The default is 32,768 tokens, capped by model limits and preserving larger loaded contexts. Both local inference paths share `Providers.modelRequest`, which rechecks after eviction, estimates request room (excluding image data), and can grow adjustable contexts up to 262,144 tokens or the model maximum. An HTTP context rejection reporting the required tokens gets one larger-context retry before the response is returned. This estimate is not a tokenizer; streaming errors, unavailable memory, server-fixed context and intrinsically oversized prompts can still require a smaller request or different model (`src/providers/api-agent.cjs`, `src/providers/providers.cjs`).

Structured calls from Hub (chat, coordination and compaction) and Smart routing use `Providers.structured` for detected local servers. They send system instructions, a bounded user prompt, optional images and an explicit JSON schema to `/v1/chat/completions`, without execution tools. LM Studio/Ollama receive `response_format.json_schema`; llama.cpp receives its `response_format.schema` form. The local Responses endpoint is not relied on for schema enforcement. JSON parsing and caller validation still fail closed: plain text, incomplete output and invalid Hub actions cannot become actions. The existing provider lock covers loading and the complete response, including cancellation. Unknown/hosted providers and subscription backends retain their existing paths. All agents share a provider-level lock across model management and streaming inference so a reload cannot interrupt another Harness response. Local inference for one endpoint is serialized. Stop prevents sending after preparation; a reload already started finishes under the lock, since canceling HTTP cannot reliably cancel server allocation. Manual load/unload is disabled while any agent is busy. Unload frees model memory and preserves downloads and conversations; a later message loads again. The composer shows Load, Loaded (context in the tooltip) and Unload for a supported selected model, including the last local worker chosen by Auto. ## Persistence and compatibility guardrails

`src/session-store.cjs` is the shared persistence boundary for controllers, orphan-worker detection and startup backups. It retains version-1 JSON snapshots and appends flushed metadata/transcript deltas to `.journal`; unchanged saves write nothing. Checkpoints flush the temporary file before atomic replacement, then truncate the journal. A snapshot revision prevents replay after a crash between replacement and truncation. A torn last record is discarded; complete malformed records and revision gaps stop loading without modifying evidence. Windows flushes files; POSIX also flushes directory entries. The runner remains the single writer.

Normal close and the 8 MiB/1,000-record threshold checkpoint the store. A failed automatic checkpoint is logged while the already-flushed journal stays authoritative. Serialization still examines all in-memory records; this removes repeated full-history disk writes, not all CPU cost or in-memory history growth. Keep JSON and journal together during backup; `backupStores` creates standalone recovery copies.

`ui/agent-state.js` supplies the same sub-bot ownership and inheritance rules to renderer and runner, including fail-closed ancestry. `ui/report-format.js` owns legacy report parsing. These modules, the store and provider contracts are checked by strict `tsconfig.json`; `npm run check` is required in CI. ### Skill comparison review safeguards (2026-10-23)

Body/resource comparisons require observed reads in both runs when their effective indexed description is unchanged. If the description changes, only the changed run must read the body: asymmetric activation can be the intended change. Description-only changes remain measurable through the index. Legacy records without description-change metadata use the stricter rule. `ToolHelpers.read` records successful named-skill reads on the current submission. `Controller.comparisonSkillReads` also accepts successful native tools from that turn with a canonical path to the frozen entry and returned body text. It handles numbered output, relative/dotted paths, nested shell quotes, nested Cursor ACP blocks, and partial reads/searches whose combined output covers every nonempty body line, including headings, within the current turn. One matching line, incomplete coverage, failures, unrelated paths and old turns cannot authorize adoption. This records observed reading, not proof that a model followed every instruction. Attempts carry evidence through `Agents.deliver` into `comparisons.runResult`; verdict and adoption both enforce it. Missing evidence remains inconclusive. Workers are directed to `router_read_output` when native file access is blocked; this grants no extra filesystem permissions.

`worker-instructions.cjs` caps indexed descriptions at 300 characters, preserving old package bodies; new oversized candidates fail before writing snapshots. Shorter bundled descriptions and defaults reduce this checkout's default instructions/index to 3,747 characters (previously 4,733). Tests bound text independently of installation path length. Adopted revisions keep bundled hashes in adjacent metadata files (outside the hashed package); mismatches or unavailable legacy provenance produce a notice without replacing the override. The primary controller displays workspace notices in the Hub and persists the last shown bundled-version notice per workspace/skill/version across chats and restarts. Dismiss removes the notice. Broken-store dismissal suppresses that same error across restarts until an observed recovery or a different error; a later recurrence notifies again.

Ordinary worker turns pin their resolved skill directories by session and canonical workspace store until settlement. Frozen comparison snapshots take precedence over ordinary pins. A Hub turn can hold multiple workspace pins without mixing their packages; pruning retains every pinned store, even if the Hub chat itself belongs to another project. Pruning also defers for active readers of the same source project and any unresolved process cleanup, then retries at settlement. Unrelated workspaces do not block cleanup. Undo restores the package and persists its card even if history writing fails; a notice reports the history problem separately. History recovery preserves the original file, reconstructs available chat records, and pins pre-recovery revision IDs until the recovery record leaves the existing 50-record retention window. I/O errors still fail closed.
