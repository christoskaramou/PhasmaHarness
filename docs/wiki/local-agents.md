- **Document worker memory (R5, fixed 2026-10-19).** pdf.js typed arrays and canvas pixels live outside the worker's 192 MB V8 heap, so each reader process now gets an OS cap of 768 MiB committed memory. Only the worker is capped, never the runner, providers or game builds.
  - Windows: one long-lived `src/document-job.ps1` per `DocumentReader` holds a private job object with `JOB_OBJECT_LIMIT_PROCESS_MEMORY | KILL_ON_JOB_CLOSE`. It nests under the runner job and libuv's job (Windows 8+). The worker is forked, its PID is assigned and checked with `IsProcessInJob`, and only then are the bytes sent. While the PID is with the helper the worker is never killed, so the helper cannot open a reused PID. The helper starts once in about 0.4 s; each assignment takes about 10 ms.
  - Linux: the worker is forked through `/usr/bin/prlimit --data=<cap> -- node …`. prlimit execs node, so the IPC channel and environment survive. `--as` would break V8's address-space reservations. A service `MemoryMax=` would cap builds and providers too, and `systemd-run --scope` would leave the service cgroup, so neither is used.
  - macOS has no cap.
  - If the cap cannot be applied (no helper, assignment failed, no prlimit), the file is not read.
  - Measured 2026-10-19 (Windows commit peaks): a 10 MB, 200-page PDF used 150 MB, a 25 MP PNG 250 MB (Electron as node and plain node agree). A 3 KB double-Flate PDF that expands to 1.5 GiB reached 3.5 GB in 6.7 s without the cap, then reported "no extractable text". With the cap it stopped at exactly 768 MiB in about 2 s. In WSL Ubuntu the worker starts at about 50–70 MB `VmData`, and 640 MB of buffers fit before the cap.
  - Hitting the cap usually kills V8 with a fatal out-of-memory error rather than raising a RangeError. Both cases report "needs more memory than Harness allows".
  - Regression: `tests/documents.test.cjs` ("decompression-bomb PDF"), using `memoryBombPdf` from `tests/fixtures/documents.cjs`. Raising the cap to 4 GiB makes that test fail. It also passes in WSL. Pool `documents`.
  - **Lost results (fixed 2026-10-19).** The intermittent "stopped before returning a result" in "opaque photos are sent as JPEG" was not the cap. That fixture peaks at about 100 MB committed under the job (`PeakProcessMemoryUsed`), against 768 MiB.
    - Cause: `src/document-worker.cjs` called `process.disconnect()` straight after `process.send()`. Node 24's disconnect only waits for queued handles, so it closes the channel on the next tick and cancels a write still waiting on the pipe buffer. The worker exits 0 and the parent gets no message. Node's async IPC write callback reports success even when the write was cancelled.
    - Only results larger than the pipe buffer are hit. Image data URLs (89–241 KB) failed 30 of 1,200 reads under six parallel loops, each with worker exit 0 and no stderr. A 2 MiB DOCX part failed 20 of 20 with no load, and a 300 KB part 4 of 20, so real DOCX reads were hit too. Full-suite load probably just slows the parent's reads (inferred; no failing suite run was instrumented).
    - Fix: disconnect in the send callback. After the fix, 0 of 1,200 image reads failed under the same load and all 20 DOCX reads passed. Under Electron 44.4.3 as node (Node 24.21.0) the 2 MiB DOCX read failed 20 of 20 before the fix and passed 20 of 20 after.
    - Full suite (`--test-concurrency=1`): 2 of about 6 runs failed before the fix; 10 consecutive runs (691–699 tests) passed with no warnings after it. Not run on Linux.
    - Regression: `tests/documents.test.cjs` ("larger than the IPC pipe buffer"). It fails against the old worker.

Assigned input boundary (verified 2026-10-18): when a live delegated worker cannot read its originating chat because that chat is Full-access or in a different workspace, `Agents.readContext` exposes only the request already assigned to that worker. Redesigned 2026-10-20 at the user's request ("use text to ask the agent again at a specific time"; verified by tests, no live firing yet): a routine is saved text that Harness sends back to an agent, as a new message in the chat where it was saved, on a schedule, once at a date and time, or on each new local Git commit. One-time routines (added 2026-10-20 at the user's request): trigger `once` with `date` (YYYY-MM-DD), `time` and `timeZone`; `routine-time.once` validates a real date, refuses a local time skipped by a spring clock change and runs a repeated autumn time at its first instant; saving refuses a time that is not in the future; after its run settles, `refreshRun` deletes the record. Records are schema 2 in the primary store (`data.routines`): `agentId` (the agent it runs on; `main` for Hub), `ownerId` (that chat; Clear moves it), `createdBy`, `name` (defaults to the start of `text`), `text`, `schedule`, `access`, `workspace`, `next`/`head`, `enabled`/`error`, `run` and `last`. When due, `Routines.fire` calls the agent's ordinary `send` with a `routineRun` marker, so the message queues behind a busy turn like a typed one; the marker is carried through the queue, failover resend, pending message, committed chat item and Hub's message, and the UI labels it "Routine · <name>". A run lasts while its message is queued or its turn runs (`live`), and the next occurrence waits for it, including across a restart. An agent that is not ready (connecting, blocked, busy in another chat, queue full) keeps the occurrence for a later tick. A run is held (disabled with an error) when its chat's access is now higher than the access approved at save, or a Git routine's chat moved to another folder; saving or resuming from chat re-approves at the lower of the routine chat's and the asking chat's access. A failed run is recorded in `last.error`, not held. Ownership rule (chosen 2026-10-20): a routine dies with the agent it runs on, so routines saved in Hub (main or group chats) persist and Hub can delegate when one fires, while a bot's own routines are deleted with the bot inside `deleteAgent`'s save (rolled back if that save fails).

Calendar misses coalesce into one admitted occurrence and advance from the current clock. Local Git HEAD triggers capture their initial baseline before acknowledgment and poll at up to 30-second intervals, sharing one read per workspace in a cycle. J5 (user decision, verified 2026-10-19): when a Git routine's run settles (its message left the queue and its turn ended), the HEAD at that moment becomes the new baseline, so the run's own commits never start it again. Any commit made before the settle, the user's own included, is absorbed; only later commits trigger. `refreshRun` saves `rebaseHead` with the finished run (restart-safe), the next cycle reads HEAD without waiting for the 30 s poll, and `save()` (edit/Resume) clears the flag because it reads a fresh HEAD itself. - **Start now** only appears for work that was queued and never started (`recovery.kind: not-started`) on a contained runner (`recoveryVersion: 1`). It reruns the original source, owner, permission, parent-revision and workspace checks; only the owner-queue pause that held it is waived. It refuses while the budget is paused, while an earlier job for that bot is undecided, and while that bot has saved messages from before the restart. The decision is saved before the job is queued, and the existing attempt counter still prevents a second automatic start after another crash.
- Work that may have run (`uncertain`) has no rerun path. Jobs saved by an uncontained or older runner only offer Return.
- `restartRecovery` keeps the first restart's record until the job resumes. A later restart of resumed work records that run as uncertain instead of keeping a stale "not started".
- Regressions in `tests/agents.test.cjs`: "returns to its owner only by the user decision", "never-started assignment held after restart", "second restart after resumed work"; UI smoke phase "restart reconciliation".

## Launching Harness from an agent session (sandbox pitfall)

Verified 2026-10-19. API providers (LM Studio, DeepSeek API, any OpenAI-compatible endpoint) no longer run through Codex. Codex may be missing from the PC and from the provider list.

**How it runs.** `capabilities()` gives provider ids without `:` an `api` capability, so `sendCLI` runs them through `ApiAgent` (`src/providers/api-agent.cjs`).
- The loop streams `/chat/completions`, asking for usage in the final chunk.

## Local model memory and context

Verified 2026-10-10. `src/providers/local-models.cjs` discovers model-management APIs at the configured provider endpoint (preserving reverse-proxy prefixes and authentication). LM Studio supports load/unload and context sizing; Ollama uses a Harness-named preset derived from the downloaded model with `num_ctx` set, because OpenAI-compatible requests do not retain a one-off native context override. These small preset definitions reuse weights; the original model is unchanged. llama.cpp router mode supports load/unload, but context size is server configuration. Unsupported endpoints and hosted providers keep their existing inference path. No model downloads are started.

Workers and the routing classifier prepare local models before inference. The default is 32,768 tokens, capped by model limits and preserving larger loaded contexts. Both local inference paths share `Providers.modelRequest`, which rechecks after eviction, estimates request room (excluding image data), and can grow adjustable contexts up to 262,144 tokens or the model maximum. An HTTP context rejection reporting the required tokens gets one larger-context retry before the response is returned. This estimate is not a tokenizer; streaming errors, unavailable memory, server-fixed context and intrinsically oversized prompts can still require a smaller request or different model (`src/providers/api-agent.cjs`, `src/providers/providers.cjs`).

Structured calls from Hub (chat, coordination and compaction) and Smart routing use `Providers.structured` for detected local servers. They send system instructions, a bounded user prompt, optional images and an explicit JSON schema to `/v1/chat/completions`, without execution tools. LM Studio/Ollama receive `response_format.json_schema`; llama.cpp receives its `response_format.schema` form. The local Responses endpoint is not relied on for schema enforcement. JSON parsing and caller validation still fail closed: plain text, incomplete output and invalid Hub actions cannot become actions. The existing provider lock covers loading and the complete response, including cancellation. Unknown/hosted providers and subscription backends retain their existing paths. Verified 2026-10-10: the running LM Studio Gemma model returned valid JSON via the documented chat endpoint, and an isolated full Hub send of `hello` completed with no agent actions or cloud calls. This live check used synthetic history only. Offline tests cover schema formats, malformed/truncated replies, context growth/retry, Stop and hosted fallback. See [LM Studio structured output](https://lmstudio.ai/docs/developer/openai-compat/structured-output), [Ollama compatibility](https://docs.ollama.com/api/openai-compatibility) and [llama.cpp server](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md).

All agents share a provider-level lock across model management and streaming inference so a reload cannot interrupt another Harness response. Local inference for one endpoint is serialized. Stop prevents sending after preparation; a reload already started finishes under the lock, since canceling HTTP cannot reliably cancel server allocation. Manual load/unload is disabled while any agent is busy. Unload frees model memory and preserves downloads and conversations; a later message loads again. The composer shows Load, Loaded (context in the tooltip) and Unload for a supported selected model, including the last local worker chosen by Auto. Status reads never load a model, refresh on focus and every ten seconds while visible, and show retry on failure (`ui/app.js`, `src/main.cjs`). Ollama's managed presets remain on disk, and its five-minute idle lifetime is retained.

Send now and live input (verified 2026-10-20): queued-message actions use Send now for every provider. Provider live-input audit (2026-10-20; documentation/source inspection, no live inference):
- Codex: native `turn/steer` is already wired in `src/controller.cjs`.
- Claude: streaming input supports multiple messages and interruption; Harness now forwards direct follow-ups, but live timing has not been measured. Reference: https://code.claude.com/docs/en/agent-sdk/streaming-vs-single-mode .
- Muse: **native queue/steer/replace is available**, not just stop/restart. Installed `@muse-code/sdk` 1.4.11 declares `IfBusy = "queue" | "steer" | "replace"` in `dist/src/msp.d.ts`; our `src/providers/muse.cjs` sends one turn then tears down its host. Reference: https://meta-models.github.io/muse-code-sdk/next/generated/msp/methods/turn-start/ .
- Cursor: local TypeScript SDK `run.steer(text)` returns `complete_delivered` or `revert_to_followup`; cloud/detached handles fall back. Our `src/providers/cursor.cjs` uses ACP, whose documented interface exposes `session/cancel`; do not assume SDK steering is available through that adapter or silently switch authentication/billing. - DeepSeek Harness: its published ACP contract allows one in-flight prompt per session and supports `session/cancel`, then subsequent prompts. A persistent cancel/re-prompt path can improve our process-kill fallback, but native mid-turn injection is not established through this interface. Reference: https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/acp/acp/README.md .
- Antigravity: documented stdin stream-json accepts multiple sequential prompts in one process, one result per turn. Our adapter already uses this transport but ends after one result. - API-backed models (including OpenRouter/local servers): `src/providers/api-agent.cjs` owns the tool/model loop. Corrections can be queued between model calls; changing an in-flight chat-completions request is not part of that endpoint. This is an implementation opportunity, not current native steering. Jev is routing/auxiliary inference in this integration, rather than an independent worker transport.
The previous universal stop-and-resume fallback is therefore not the best available implementation for Muse, Cursor SDK, persistent Antigravity sessions, or Harness-owned API loops. This audit changes documentation only.

Native Send now per provider (built 2026-10-20 by Claude from the audit above; fixture-tested, no live inference). `src/providers/capabilities.cjs` declares `liveQueue` (the running turn accepts follow-ups into the provider's own queue) and `liveSteer` (Send now applies within the running turn); `Controller.sendCLI` hands the run an input callback for either, and `queuedMessage` passes `{ steer }` so Send now steers where the provider can. `flushLiveQueue` feeds ordinary queued messages only to `liveQueue` providers, so a steer-only provider is never interrupted by them. A message counts as delivered only when the provider acknowledges it; otherwise it stays queued (with `uncertain` only for timeouts and disconnects).

| Provider | Follow-ups while working | Send now | Delivered when |
| --- | --- | --- | --- |
| Codex | sent after the turn | native `turn/steer` | Codex accepts the steer |
| Claude | its stream-json queue (answered after the current step) | same queue (tooltip says so) | replay acknowledgement (UUID) |
| API / local models | next model call | next model call | the message goes into a model request; one still waiting when the turn ends returns to the Harness queue |
| Muse | `turn/start` `ifBusy: queue` (a new turn the run also waits for) | `ifBusy: steer` (same turn id) | steer: `turn/start` acknowledged; queued: its turn completed (a run that fails first leaves it queued as uncertain: "closed before the queued message ran") |
| DeepSeek Harness | after the turn (one prompt at a time) | `session/cancel`, open approvals answered cancelled, the cancelled prompt's commands swept by `stopStartedSince`, then a new prompt in the same session and process | the replacement prompt is sent |
| Cursor | after the turn | same as DeepSeek over its ACP connection | the replacement prompt is sent |
| Antigravity | after the turn | stop and resend with history (fallback) | — |

- Scope: direct chats. Delegated assignments keep the revision workflow (`Agents.revise`: Codex `turn/steer`, otherwise stop and replace) with its ownership, budget and cleanup guarantees; `flushLiveQueue` and the live path skip delegated sessions.
- Antigravity keeps the fallback because its stream has no event that confirms a second prompt was received; a write followed by a crash would leave the message's fate unknown.
- Risk to check live: the DeepSeek/Cursor sweep stops every process the host started after the cancelled prompt began. A long-lived worker that dsh or cursor-agent first starts during a tool call would be stopped too (fixtures have no real process tree, so they take the no-sweep path). - Each replacement prompt gets its own approval signal, so an Allow answered after Send now cannot approve the new prompt's tools (DeepSeek captures the signal per request; Cursor checks it after the answer).
