# PhasmaHarness implementation plan

Draft plan · 18 October 2026

Implement the [design](design.md) in small working slices. Keep the app usable at every step. Use one [minimal Grok Bot-inspired chat layout](ui-templates.html) with Dark, Light, and System appearance settings. System is the initial default. Both palettes use the same components, behavior, and data.

## Completion gates

The requested end state includes every phase below, followed by a review and a running preview. Passing a fixture does not certify a live provider or deployment.

- [x] Minimal chat, separate Hub area, Dark/Light/System, quiet composer and dismissible Options.
- [x] Persistent result cards, busy-recipient queues, correlated mailboxes and independent queued cancellation.
- [x] Explicit result ownership transfer with durable acceptance, stable retries and original cancellation ancestry.
- [x] Content revisions, bounded background slots and separate foreground chat contexts; deterministic checks pass.
- [ ] Applied steering, safe replacement execution and cancellation of the selected job subtree.
- [ ] Muse Code, Antigravity and DeepSeek Harness adapters with native setup, permissions, tools and protocol checks (Gemini CLI removed 2026-10-19; Antigravity serves Gemini models).
- [ ] Always-on runner, reconnect, start at sign-in, safe restart reconciliation and update coordination.
- [x] Shared job budgets, validated artifact actions and independent Git batch project copies.
- [ ] Verified game builds, launch/gameplay checks and morning summaries.
- [x] Groups and explicit @mentions without broadcast or permission escalation.
- [x] Durable timezone-aware routines (repeating, one-time and Git triggers), missed-run deduplication, managed only by asking in chat.
- [x] Text/code, images, extracted PDF/DOCX text and local Windows voice input; human microphone acceptance remains open.
- [ ] Authenticated remote runner deployment and phone access.
- [ ] Full acceptance scenarios, code review, relevant checks and launch for user inspection.

## Step 1 Build the minimal chat UI and appearance settings

Keep a small bot sidebar, a quiet header, a centered conversation, and a persistent composer. Specialist rows show one short latest-message preview and a small activity indicator; search/new-chat controls stay compact at the top and Settings stays at the bottom. The narrow sidebar retains a separate Hub shortcut above the specialists. Reuse existing chat selection and history; these are presentation changes, not a second conversation model.

Define shared CSS color tokens for two neutral palettes. Add Dark, Light, and System to Settings → Appearance, persist the selected mode as a UI preference, and apply it before first paint. Explicit Dark or Light overrides the OS until the preference changes.

Changing appearance updates only the UI attribute/tokens or color scheme. It must preserve the draft, scroll position, focus, jobs, permissions, and provider connections, without an inference call or a page reload. Do not create separate markup, stylesheets with duplicated components, or rendering paths for each appearance mode.

Keep chat central, provider settings secondary, and handoffs expandable. Add compact job activity and result cards, attachment affordances, and clear Received, Queued, Applied, and Stopping feedback. The default view has no required job-management dashboard. Preserve existing permission dialogs and keyboard controls.

Use deterministic fake workers to demonstrate that typing, navigation, and Stop remain responsive during long work and high output. Capture baseline input latency, persisted receipt time, event display latency, and model response latency separately. Apply the design's p95 targets; do not claim faster model responses from UI acknowledgments.

## Step 2 Complete asynchronous delivery and ownership

Extend `src/agents.cjs`, `src/tools/agent-tools.cjs`, `src/controller/coordinator.cjs`, and existing persisted task records. Keep one authoritative job identity and owner; distinguish child assignments from informal bot messages. Add stable message IDs, source/destination, job correlation, revision, and delivery acknowledgment to the existing queue model.

Assignment submission returns after durable acceptance. A busy recipient queues work instead of rejecting every assignment. Questions and answers use a mailbox that remains serviceable while an assignment waits on a helper. Preserve non-escalating access, context-read boundaries, cycle prevention, and original user intent. Commit an ownership transfer as one authoritative state change after the recipient accepts; never leave two final-result owners.

Use retryable delivery plus receiver deduplication. Persist a result where the user can see it even before the owner's next model turn. Coalesce routine progress, retain all terminal outcomes, and batch background replies so they do not monopolize Hub. Direct user messages take priority while FIFO order is preserved within each relevant stream.

Separate pending queue capacity, running-worker capacity, and delegation depth. Two background execution slots bound delegated turns and automatic worker replies; FIFO waits happen before provider submission, idle helper waits release slots, and Stop cancels admission without starting a provider. Direct foreground turns and Hub coordination bypass background capacity. Automatic replies wait for capacity before occupying a public chat, so a new user question can still start. Retain hard limits and reject queue overflow explicitly. Legacy conversations and uncertain execution are not replayed automatically.

Implemented context split: the existing controller remains the bot's visible chat; delegated assignments use one lazily created, persisted execution controller per bot. Both reuse the existing provider, mailbox and queue implementation and participate in capacity, cleanup, approvals, backups and restart reconciliation. One sidebar entry remains. Nonmodal job details show the actual saved assignment and accept correlated updates without changing the chat draft. Background approvals open only through explicit Review. Access/workspace changes, clearing and deletion account for both contexts. Registered worker stores reopen without inventing bots; unregistered nonempty stores remain untouched for review. Messages retain their original receipt across destination-context changes.

Delivered: worker results persist in the owner conversation before review, survive a full/paused queue, roll back failed saves, and deduplicate delivery retries. Busy-recipient FIFO queues and question/answer mailboxes use stable IDs, persisted acceptance, receiver deduplication, bounded queues, direct-user priority, permission checks and targeted cancellation. Native resume retains local receipts. Ownership transfer saves receiver acceptance before committing the single owner, rejects stale versions/access escalation and retains original cancellation ancestry. Failed notifications preserve the committed owner and can be retried without another worker. Content revisions, separate foreground/background contexts and provider-confirmed correction handling pass deterministic fixtures. Contained Windows restart resumes compatible, versioned queues only when no provider submission was attempted; uncertain/legacy execution remains Needs review. Live-provider verification and reconciliation of uncertain execution remain unfinished. A single local model endpoint can still serialize actual inference; UI admission does not establish model-response latency.

**Done when:** A delegates to busy B and can immediately answer the user; B asks A a question without deadlock; results arrive once after a simulated delivery retry or restart. Full queues and ownership-transfer interruption preserve acknowledged work. Extend `tests/agents.test.cjs` and `tests/coordinator.test.cjs`.

## Step 3 Make steering and cancellation reliable

Update `Controller.send`, `queuedMessage`, `stop`, provider capability handling, and the UI. Status questions read saved job state without waiting for the worker. A requested change is correlated to its job, acknowledged immediately, and marked applied only after the provider accepts it or replacement execution begins with it.

Use native steering where available. For unsupported active turns, request cancellation, confirm process cleanup, and continue with saved context and the new instruction. If cleanup or delivery is uncertain, remain Waiting and explain why; never start a competing writer. Keep foreground conversation separate from lengthy specialist execution.

Make Stop a direct runner command. Cancel the requested job subtree, not unrelated jobs. A stopped parent cannot be revived by late child output or automatic continuations. Preserve artifacts and show cancellation completion independently of model availability. A changed job revision invalidates stale proposed actions while retaining prior evidence.

Reuse existing command payloads, validate them at the boundary, and keep snapshots separate from incremental events. One runner instance owns storage and processes; reconnecting clients cannot launch another copy.

Coordinate updates with the runner so an installer cannot replace active execution files or orphan processes. Headless operation preserves approvals as waits rather than bypassing them.

On startup, reconcile process identity, acknowledged messages, queued jobs, and uncertain in-flight actions. Automatically resume only known-safe work. Test failure between each persistence/delivery boundary. Keep a backup before storage migration and a documented rollback path; do not rewrite provider credentials or current conversations.

This is still filesystem separation, not an OS sandbox or proof that a generated game plays correctly.

## Follow with groups and routines

Add group chats and @mentions over the same asynchronous mailbox, ownership, access, and result rules. Group membership does not grant file or tool access. Keep one owner per outcome; group conversations do not broadcast every message to every model by default. Show only useful handoffs and let the user open the underlying detail.

Current group slice: groups are durable Hub-owned conversations with existing members, a separate sidebar list and a small member picker. A leading `@Name` sends one ordinary assignment directly, preserving the selected bot and permissions without a Hub inference call. Other members receive no call; unmentioned messages use Hub. Replies and relevant context resolve to the originating group, while its draft, queue and activity remain separate from other chats. Stop is scoped to that group; archive and removal of a working member reject outstanding assignments. Clear preserves membership and the pinned Hub conversation. Creation, failed saves, permissions, context, busy queues, restart/migration, cancellation and UI controls pass deterministic tests. Native-provider live acceptance remains part of the overall acceptance gate.

Add a small durable routine scheduler inside the runner. Persist owner, workflow reference, timezone, next run, limits, and occurrence identity. Deduplicate restarts, prevent self-overlap, and coalesce missed runs. Schedule creation/edit/pause happens through chat with a clear next-run summary. Add event triggers only after scheduled execution is reliable.

Current routine slice (redesigned 2026-10-20 at the user's request; supersedes the workflow-replay slice): a routine is saved text that Harness sends back to the agent, in the chat where it was saved, on a schedule (local weekdays, time and timezone), once at a date and time (it then removes itself) or on each new local Git commit. Routines are created, changed, paused, resumed, removed and reported only by asking in chat through the `routine` and `routines_report` tools; there is no routine UI or IPC. Hub sees and changes every routine; a bot sees only its own, and a bot's routines are deleted with it. Only a message the user typed in that chat can change routines: assignments, automatic results and mail, routine runs, wiki proposals and Harness correction turns cannot. A run waits while its message is queued or running, also across a restart; an unready agent keeps the occurrence; raised chat access holds the routine until it is saved again; a Git run's own commits become the new baseline. Spring gaps are skipped, autumn folds run once and missed runs coalesce. Fixture tests cover these paths; a live recurring run remains part of the acceptance gate.

Then add voice input, remote runner deployment, and phone access. Remote execution requires authenticated transport, secure credential provisioning, artifact transfer, and a suitable runtime host; it is not merely opening the local port to the internet. Preserve the same chat and asynchronous protocol across hosts.

Current file-input slice: the composer selects/pastes up to four text/code files, images or PDF/DOCX text snapshots. Original documents are limited to 10 MB; PDF reading accepts up to 200 pages and all text snapshots share the existing 64 KB limit. A separate owned process runs PDF.js and bounded ZIP extraction, with a 15-second timeout, a 768 MiB OS memory cap (Windows job object, Linux prlimit) and confirmed cancellation. Word XML rejects DTDs, entities, malformed structure and excessive formatting. Oversized or empty text rejects without truncation or discarding existing drafts. Document chips and sent summaries identify extracted text; layout, images and annotations are excluded. Draft chips, file-only Send, failed-send recovery, recall, queued Edit, literal collapsed display, native history retention and export have deterministic checks. Actual PDF/DOCX parsing and Unicode document Send pass in Electron; the mixed Gemini/Muse fixture also reads saved attachment snapshots through Harness context. Originals are not persisted, and snapshots grant no additional filesystem permission. OCR, legacy DOC, spreadsheets and presentations are outside this text-input slice.

Current voice slice: a small microphone control uses the installed Windows speech recognizer, with its language shown in the tooltip and a visible listening state. No microphone starts at launch. Words enter the originating draft; Send stops recognition and includes its final words once. Navigation, dialogs, window hiding/focus loss and Quit stop the owned speech process. Failed cleanup blocks another recording. A five-minute limit bounds each recording, and oversized drafts retain their words for editing. Missing speech support is explicit, with no transcription API fallback. Native recognition passed with a generated English WAV; UI/process tests use fake audio and cover final words, double Send, late output, original-chat binding and cleanup. Human microphone quality remains unverified.

Current browser-access slice: the same runner exposes an opt-in loopback HTTP listener, authenticated command dispatch, revocable persisted sessions and reconnecting snapshots. A configured external origin requires HTTPS through a private proxy; its Host and Authorization headers must be preserved. Native IPC keeps its sender checks, and both paths reuse existing controller validation and job ownership. Settings controls start/stop, connection links and revocation. The shared frontend now works at phone width, including a held fake-model request, independent typing/Stop, request-scoped confirmation, actual local PDF extraction, UTF-8 streaming, enlarged Settings and local appearance. Browser keys never become provider credentials or child environment variables; reset invalidates prior connection links. Native account setup and Windows microphone controls stay on the desktop. Published files and ZIP folder snapshots now download through bounded private staging and one-use file capabilities; expiry, revocation, Stop and Quit release staged files. File fingerprints and receipt versions are rechecked, and active Harness writers block preparation. An actual browser download verifies included assets with fake model inference. Private Linux service recovery is verified with fake native inference. Public-host deployment and real phone/network acceptance remain unfinished, so the full remote gate stays open.

### From the 17 October roadmap

The original twelve-step roadmap (Usage question session, 17 October) maps onto this plan as follows. Deferred by the design and still wanted:

### From harness2 (google-research/harness2 at `1cfe254`)

Codex compared harness2 with PhasmaHarness on 20 October; its claims about our code and the cited harness2 lines were spot-checked (no harness fingerprint exists here; their selection pool excludes the baseline; each mode schedules 4k rollouts and 3k improvement stages; lesson verdicts are helped, hurt, no observed effect and confounded). Borrow the method, not their Python framework.

1. **Setup fingerprint (first).** Save with every task and job result a hash, plus readable parts, of what shaped the run: bot instructions, selected skills, tool configuration, provider CLI and its version, model and effort. Cheap, no model calls. Makes "the same setup worked yesterday" checkable and is the precondition for comparisons.
2. **Richer lessons.** Extend `src/lessons.cjs` records, not a new memory system: the situation where the lesson applies, the actual change that fixed it, the supporting evidence, a confidence, and a verdict of helped, hurt, no observed effect or confounded. Record no lesson when evidence is thin.
3. **Opt-in two-run comparison.** Same task, identical project copies, same model and checks: one run with the current instructions, one with a single changed instruction or skill. Compare correctness, cost, time and corrections needed. One baseline and one candidate, never recursive experiments on every request. The baseline always may win: keep the current setup unless improvement is shown. Candidates cannot weaken permissions or change acceptance checks. Blind the comparison to reduce preference bias.
4. **Proven setups.** Keep a small versioned, approved setup per recurring kind of work (for example Vulkan debugging, document generation) with its evidence and a rollback path. Extends bot instructions and skills; never rewrites the project wiki or rules automatically.
5. **Earlier harness2 ideas (offered 19 October).** Best-of-N runs with a composed answer; per-agent harness pieces; tuning suggestions from recorded outcomes; a dry-run preview of what a request would do; a viewer for saved lessons.

Their reported gains are not evidence for PhasmaHarness until measured here. Every experiment is opt-in, bounded and paid only when the user asks.
